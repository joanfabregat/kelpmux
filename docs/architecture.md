# Architecture

Native Kelpmux is a Linux terminal multiplexer with a persistent server and separate attached clients. The server, [KelpServer](https://github.com/joanfabregat/kelpserver), lives in its own repository and owns PTYs, interactive shells, terminal emulation, per-pane leases and sizes, agent metadata, activity history and client authorization. Since KelpServer 0.3 it is a generic session server that speaks only the pane stream: the composed-screen protocol 58 and all server-side UI (tabs, parking, focus, dialogs, layout) are gone. Its design is described in [KelpServer's architecture](https://github.com/joanfabregat/kelpserver/blob/main/docs/architecture.md). This repository contains the frontend (TUI), the web client and the optional tmux adapter. The frontend owns raw terminal input, escape framing, local shortcut routing and ANSI rendering. KelpMux requires KelpServer 0.3 or later and builds against the revision pinned in `Cargo.toml`.

## Server boundary

The TUI attaches to KelpServer over its versioned, length-prefixed JSON protocol on a same-user Unix socket, as a client of the pane stream (v1); see [TUI on the pane stream](#tui-on-the-pane-stream). Pane input and size follow per-pane leases, and the same-user `ctl` command (`list`, `new`, `reclaim`, `shutdown`) administers the server through the stream session API on a connection of its own, without subscribing to screens or keeping a lease. PTY lifetime belongs to the server: detaching or losing a frontend leaves its shells and agents running. The pane stream is documented in the [KelpServer stream contract](https://github.com/joanfabregat/kelpserver/blob/main/crates/server/docs/native-client-protocol.md).

Discovery, the metadata journal, activity history, closed sessions and recovery are server behavior; see the KelpServer documentation for their rules. Grid geometry, tab order, parking, close handling and the scratch marker are TUI state.

## Frontend input and rendering

The frontend enters raw mode, draws changed ANSI cells and restores its terminal state on normal exit and handled termination. Its incremental decoder recognizes SGR mouse reports and bracketed paste across reads. Escape timeout allows standalone Escape while retaining ordinary Alt sequences. Paste payloads bypass prefix routing entirely; oversized paste is truncated without releasing remaining payload as application keys or actions. The router owns Ctrl-B sequences and preserves application editing bytes outside its named bindings.

Header controls, tabs, sidebar targets and footer actions share hit geometry with the input router. When application mouse reporting is enabled, the server translates frontend coordinates into terminal coordinates and honors click/drag/motion modes. Otherwise the router emits body-local selection actions and copies on release; Shift selects or scrolls locally even in mouse-aware applications. Help, configuration and confirmations use centered dialogs that consume application input and close through their controls or outside clicks. A close request initially selects Close; Enter confirms and Escape cancels. The server accepts confirmation only for that dialog's pane before ending its owned process tree.

## Workspace lifecycle and UI configuration

A named workspace selects its private state directory and socket. `kelpmux start` creates an explicit persistent instance by launching the `kelpserver` executable (beside `kelpmux`, or `KELPSERVER_BINARY`, or `--server-binary`), `attach` connects without replacing the server, `status` inspects it, and `stop` sends the stream `shutdown` request to that instance. Startup validates names and live endpoints, avoids duplicate instances, and reports failures rather than silently replacing another workspace. `ssh-entry` is a login entry point that starts or attaches the selected workspace; SSH authentication and terminal transport remain the client's responsibility.

UI configuration is bounded JSON, validated before the server starts. It defines a prefix, reading dimensions and explicit key/action bindings. Application bytes outside those bindings pass through; terminal escape/paste framing remains separate from shortcut interpretation. UI selectors share geometry for grouped settings, parked-tab restore targets, agent attention/finished filters and pane movement.

## TUI on the pane stream

Per [KelpServer ADR 0002](https://github.com/joanfabregat/kelpserver/blob/main/crates/server/docs/adr/0002-generic-session-server.md), TUI state moved out of the server. `kelpmux attach` is a TUI built on the pane stream and session API: KelpServer keeps sessions, PTYs, terminal state, leases, spawn/close/restore, closed-session records, observations, notifications and lifecycle, while KelpMux renders locally and owns tab order, names, colours, parking, focus history, dialogs, grid geometry, the scratch marker and settings. The renderer, workspace model and UI types live in KelpMux: `src/native/render.rs`, `workspace.rs`, `status.rs`, `ui.rs` and `protocol.rs` (`Frame`, `Action`, `UiMessage`), started as copies of KelpServer's composed implementation, which ADR 0002 step 3 deleted (KelpServer 0.3). `src/native/tui/` holds the controller (stream events and routed input in, stream requests out), the terminal loop and the persisted state (`tui-state.json`, see the [native guide](native.md#persisted-ui-state)). The server starts with zero panes and the TUI creates the tabs. KelpMux's part of `workspace.json` (the startup template and `ui` settings) and the read-only parsing of the composed UI's legacy files for the TUI's one-time migration live in `src/native/config.rs`; KelpServer records only `shell` and `cwd` there and keeps the other keys. `ctl`, `stop` and the web bridge use only the stream session API (`src/native/session.rs`, a one-shot session client, kept beside KelpServer's smaller `connection::Session` because it also covers the web bridge's peer-checked sockets, leases, session data and the longer `closed_sessions` wait); `kelpmux diagnostics` uses the one-shot `Diagnostics` record KelpServer keeps for tools without a stream session. The Status dialog's presentation (`status::View`, `Sort`) is KelpMux's; only host sampling (`Monitor`, `Snapshot`) comes from KelpServer.

`kelpmux web-relay` uses KelpMux's own copy of the web relay (`src/native/web_relay.rs`), moved from KelpServer (which removed its copy in 0.3.0-beta.2), which serves PNG, web manifest and JSON assets with their media types under `X-Content-Type-Options: nosniff`.

## Legacy compatibility and distribution

Legacy commands use an explicitly selected unmodified tmux 3.8+ executable and socket. tmux owns those PTYs, terminal rendering, layout, mouse, key tables and client size policy. Kelpmux supplies metadata, guarded layout helpers, floating reading geometry, optional lifecycle hooks and generated example bindings. Native and legacy state should be isolated; neither path automatically replaces configuration, starts a daemon or migrates an existing workspace.

CI tests real native PTYs, emulation and input on Linux x86-64 and ARM64 against the pinned KelpServer, plus Rust 1.89 and dependency advisories/licenses. Separate compatibility jobs build checksum-verified upstream tmux 3.8 and exercise private tmux servers. Release archives package `kelpmux` and the pinned `kelpserver`, project licensing and documentation with SHA-256 checksums. tmux is an optional separately installed legacy dependency and is not bundled in native archives. Starting a named workspace launches its private persistent server explicitly; nothing installs a system service, launches a user agent or performs automatic recovery.

CI cache keys separate compiler versions, architectures and test jobs. PR runs never save cache artifacts, release compilation has read-only repository permissions, and release uploading occurs in a distinct minimal job after both architecture builds succeed. Fresh advisory checks run even when the pinned audit executable or compiled targets are restored.
