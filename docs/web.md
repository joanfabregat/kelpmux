# Web client

KelpMux includes an optional browser client for the same persistent workspaces as the TUI. It is centred on terminals, with the TUI's feature set adapted to the browser (see [Feature parity with the TUI](#feature-parity-with-the-tui)): a left sidebar of terminals with agent state, a read-only live grid for monitoring, parking, a Terminals table (every terminal with its agent state, folder, Git repository and branch, running program and last activity), per-terminal notifications, recently closed terminals, search, selection and copy, links, keyboard scroll and selection modes, [file and image uploads](#uploads) dropped onto a terminal, a [file browser and text editor](#files) for the server user's files, settings for appearance, alerts, keyboard shortcuts, uploads and security keys. It has no projects, Git views or operations; those belong to KelpHub. (The Terminals table only shows, read-only, which repository and branch a terminal's folder is in, with a link to GitHub.) [ADR 0003](adr/0003-web-client-in-kelpmux.md) records why it lives here and what it must not become.

The browser signs in with a hardware security key (WebAuthn) and runs OpenSSH itself, compiled to WebAssembly. The SSH session ends in the browser; nothing on the server side ever holds the session keys or a private key.

## Components

```text
browser ── HTTPS + WSS ──▶ kelpmux web-relay ── TCP ──▶ sshd ──▶ kelpmux web-bridge ──▶ workspace socket ──▶ KelpServer
 (React UI, OpenSSH/WASSH,      (static assets,              (user's          (stdio, same-user        (PTYs, emulation,
  WASM terminal core)            byte relay)                  account)         peer check)               processes)
```

- `web/`: the React/TypeScript browser client. The reusable terminal pieces come from KelpCore's `@kelpcore/web` package (see [Reusable terminal component](#reusable-terminal-component)); `web/src` is the KelpMux application shell around them.
- `kelpclient` (KelpCore's `crates/client`, a Git dependency), compiled to `wasm32-unknown-unknown` and served as `client-core.wasm`: stream framing, validation, history layout and selection shared with native Rust clients.
- KelpServer and `kelpclient` come from the [KelpCore](https://github.com/joanfabregat/kelpcore) repository at the revision pinned in `Cargo.toml`, so `client-core.wasm` is built with `kelpclient-protocol` from the same revision as the server; `@kelpcore/web` in `web/package.json` pins the same KelpCore commit. KelpMux requires KelpServer 0.3 or later, which speaks only the pane stream (no composed protocol 58) and starts a workspace without panes: the first client creates them. The web relay is KelpMux's own (`src/native/web_relay.rs`); KelpServer removed its copy in 0.3.0-beta.2. Since that release (`kelpclient-protocol` 0.3.0) the pane list has no `number` or `parked`: the browser numbers terminals by their position in its own order (`numberPanes` in `web/src/layout-store.ts`), so without a stored order the numbers are the creation order, as before, and it keeps parking in its layout store.
- `kelpmux web-relay --config PATH`: serves the embedded static assets and forwards WebSocket binary bytes to one operator-configured SSH destination. It has no key enrollment API, holds no SSH private key, never terminates SSH and has no code path to a workspace socket. Before forwarding the server's first SSH reply it checks that the host key matches the configured `ssh_host_key`; browser OpenSSH verifies the same key and its signature independently.
- `kelpmux web-bridge --workspace NAME`: run by OpenSSH as the authenticated Linux user, without a PTY. It connects to that workspace's existing private socket, checks that the peer is a process of the same user and stays bound to that process, then relays the independent pane stream plus a small set of request-correlated operations. It never listens on TCP and never stops, restarts or replaces a workspace server. If its workspace's server is not running (no socket, or a socket nothing listens on), it tells the browser, which shows a **Start workspace** button; only that explicit click sends `start`, which runs the same code path as `kelpmux start --workspace NAME` for the bridge's own configured workspace and nothing else (no workspace name, server binary or replacement comes from the browser), and is refused while a server is running. The bridge then connects as usual. KelpServer removes agent and multiplexer session markers from the environment of the server it starts and of every pane shell (see [native.md](native.md)).

The `Web` operations the bridge accepts (API version 3, minor 3) are `state`, `new` (a shell in a new pane, optionally in a given absolute directory), `close` (explicitly confirmed), `search`, `history`, `status` (system status and processes), `closed` (the server's closed-session records the TUI's Recovery lists: recently closed terminals and previous runs, with their restore choices) and `restore` (explicitly confirmed: resume an agent conversation, rerun a command or open a shell in the original folder, in a new pane through the server's `restore`), `repos` (see below), `commands` (each live pane's foreground program, keyed by pane id: the base name of the first argument of its terminal's foreground process-group leader, or `null` when the pane's own process is in front, such as a shell at its prompt; process identities come from the server, never the browser, and arguments are never returned because they can hold secrets; at most 128 panes) and `start` (only while the workspace server is stopped; see above). Each operation that reaches the server uses KelpServer's stream session API on a short-lived connection of its own, checked to reach the same server process and epoch as the relayed stream: `new` is `spawn` (idempotent per browser request identity), `close` takes the pane's lease and sends `close`, `search` and `history` are the stream requests of the same names, `closed` is `closed_sessions`, `restore` is `restore` for a record of the server's latest list, and `commands` reads the pane list of the first update. While stopped, the bridge answers the stream `hello` with a `{"Workspace":{"running":false,"workspace":NAME}}` notice and accepts only `state` and `start`. Stream requests, notification acknowledgements included, are forwarded unchanged; read marks are shared with the TUI. Every other method is refused with `unsupported web operation`. A web build refuses a bridge of another API version (and the reverse) with a message asking for matching versions; both ship in the same `kelpmux` binary. Version 3 removed `color`: tab colours are each client's own state ([ADR 0002](https://github.com/joanfabregat/kelpcore/blob/main/crates/server/docs/adr/0002-generic-session-server.md), decision 144b), and the web client has since dropped tab colours altogether (decision 177). Operations added within a version are additive: `state` reports `api_minor` (3 in version 3) and its `operations` list, and the web client uses an optional operation (`repos`, `commands`, `uploads`, `files`, `downloads`) only when that list names it, so an older bridge of the same version still serves a newer web build with those columns left plain, uploads off, no Files entry and no Download actions. Minor 1 added `uploads`, which is not a `Web` method: it says the bridge relays KelpServer's upload stream requests (`upload_begin`, `upload_chunk`, `upload_finish`, `upload_cancel`) and their events like any other stream request, unchanged, on the relayed connection (a bridge of minor 0 cannot parse them and would end the session). See [Uploads](#uploads). Minor 2 added `files`, which is not a `Web` method either: it says the bridge relays KelpServer's file stream requests (`file_list`, `file_stat`, `file_read`, `file_write`, `file_mkdir`, `file_rename`, `file_trash`, `file_delete`) and their replies (`file_list`, `file_stat`, `file_content`, `file_written`, `done`, `file_removed`, `file_error`) unchanged, with the Welcome's `file_limits`, on the relayed connection (a bridge of minor 0 or 1 cannot parse them and would end the session). See [Files](#files). Minor 3 added `downloads`, again not a `Web` method: it says the bridge relays KelpServer's download stream requests (`file_download_begin`, `file_download_ack`, `file_download_cancel`) and events (`file_download_started`, `file_download_chunk`, `file_download_done`, `file_error` with a `download`), and the Welcome's `file_limits.downloads`, unchanged (a bridge of minor 2 or older cannot parse them and would end the session). See [Files](#files) (Downloads).

**Binary screens.** When the server's Welcome lists `binary-screens`, the browser's `Session` (in `@kelpcore/web`) sends the `binary_screens` stream request, which the bridge forwards like any other, and from then on the server follows each `update` with one binary screen record ([KelpCore binary-screens.md](https://github.com/joanfabregat/kelpcore/blob/main/crates/server/docs/binary-screens.md)). The bridge reads the server's records raw: JSON records are decoded and re-serialized as before, binary records (payload starting with `0x00`) are written to the browser byte for byte without parsing, in order, through the same bounded queue, and only after the Welcome has been relayed. The browser's WASM core decodes them into the ordinary JSON updates the rest of the client uses. A 300 × 80 snapshot is then about 16 KB instead of about 2.4 MB of JSON. The web assets rely on this bridge behaviour and need no extra negotiation, because the relay serves the assets embedded in the same `kelpmux` executable that runs as the bridge; an older bridge re-serializes every record as JSON and would end the session at the first binary record. The TUI opts in the same way and decodes the records natively (`tui::attach::Records`); the one-shot session API connections (`kelpmux ctl`, the bridge's own `Web` operations) never opt in and stay JSON.

`repos {"paths": [...]}` takes pane working directories (which the browser already has) and returns `{"repos": [...]}` in the same order, each entry `{"root", "branch", "detached", "github"}` or `null`. `root` is the directory holding `.git`; `branch` is the checked-out branch (`refs/heads/` removed); `detached` is the first twelve hex digits of a detached HEAD; `github` is `owner/repo` when the preferred remote (`origin`, else the first remote in the config) is on GitHub in its `https://`, `ssh://` or `git@github.com:` form. Credentials in a remote URL and non-GitHub remote URLs are never returned; such a repository shows its root without a link. The bridge computes this itself; KelpServer is not involved. It only reads files and never runs `git` or any other process: `.git` (a directory, or a file whose `gitdir:` names a linked worktree's or submodule's Git directory), `HEAD`, a worktree's `commondir` and the shared `config`. It is bounded and conservative: at most 64 paths per call (more is an error), only absolute paths without `.` or `..` components that are directories owned by the bridge's user, at most 32 directories walked up from each, Git metadata owned by another user or reached through a symlinked `.git`, `HEAD` or `config` is ignored, files are opened without following symlinks and without blocking (a FIFO cannot stall the bridge), `HEAD`, `.git` and `commondir` above 4 KiB and a config above 64 KiB are not parsed (the repository is still reported, without a remote), and config `include`s and `insteadOf` rewrites are not followed. Results are cached for one call only.

## Security boundaries

- Authentication is SSH public-key authentication by the host's OpenSSH server. There is no web password, cookie or session token. Each new SSH connection authenticates again.
- A key authorized for a Linux account grants that account's terminals, which run commands with that user's authority. Operators who want the key limited to the web bridge can authorize it with `restrict,verify-required,command="/path/to/kelpmux web-bridge --workspace NAME"`; this prevents unrelated SSH commands and forwarding, but a shell in a pane is still a shell.
- Run the relay under a separate restricted service identity (or an equivalent container) with no access to user home directories, credentials, workspace sockets or other processes. Putting the relay and the bridge in one executable is packaging, not isolation.
- The origin that serves the JavaScript and WebAssembly is trusted: a compromised frontend can read terminal contents and input even though the relay only sees SSH ciphertext. Serve it over HTTPS only, from a trusted build.
- The relay sets cross-origin isolation headers (required by WASSH), a restrictive Content-Security-Policy, `nosniff` and `no-referrer`, checks the `Origin` of WebSocket upgrades, and bounds headers, frames, buffers, connections and time.
- Browser storage holds only public data: credential handles, public keys, SSH fingerprints, key names/icons/colours, appearance, this browser's layout and its default upload folder. No private key, SSH transport state or token is stored, exported or shared with other pages.
- The upstream OpenSSH WASM build (`0.82`, OpenSSH 10.6 with OpenSSL 1.1.1w) and the WASSH JavaScript are fetched at pinned, checksum-verified revisions. RustSec and npm audits do not cover the compiled libraries inside that archive; treat the legacy OpenSSL copy as needing its own review before exposing the client beyond a private network.

## Build

The relay serves assets embedded at compile time from `web/dist`. A checkout without `web/dist` builds and runs the TUI and server normally; `kelpmux web-relay` then refuses to start with an explicit "no web client assets" error.

Prerequisites: Rust with the `wasm32-unknown-unknown` target and Node 24. Keep dependency fetching and auditing separate from building, and run builds in your usual isolated environment:

```sh
# 1. Portable terminal core for the browser (kelpclient, from the pinned KelpCore revision).
cargo build --locked -p kelpclient --release --target wasm32-unknown-unknown
cp target/wasm32-unknown-unknown/release/kelpclient.wasm web/public/client-core.wasm

# 2. Pinned WASSH and OpenSSH WASM (download and verify only; executes nothing).
bash scripts/fetch-web-ssh.sh

# 3. Locked JavaScript dependencies (with @kelpcore/web from GitHub at the pinned
#    KelpCore commit), without install scripts, then audit.
(cd web && npm ci --ignore-scripts && npm audit --audit-level=high)

# 4. Test, type-check, lint the React hook rules (oxlint) and build the static client.
(cd web && npm test && npm run check && npm run lint && npm run build)

# 5. Build kelpmux, which embeds web/dist.
cargo build --locked --release --bin kelpmux
```

Build the web assets before compiling the executable that embeds them; rebuild `kelpmux` after every web change. `node_modules`, `web/dist`, `web/sourcemaps`, `web/public/vendor` and `web/public/client-core.wasm` are generated and ignored by Git. `npm run build` also writes the client's source maps to `web/sourcemaps/` (never to `web/dist`, so they are neither embedded nor served) and its release name to `web/sourcemaps/RELEASE`; see [Error reporting](#error-reporting).

`npm test` runs the application's unit tests (`test/*.test.mjs`) with `node --import ./test/ts-loader.mjs`: Node strips TypeScript types itself but refuses to under `node_modules`, so that small load hook strips them from `@kelpcore/web` with Node's own `module.stripTypeScriptTypes` (no extra dependency). The terminal layer's own unit tests (keyboard, keys, key mode, mouse, wheel, touch keys, uploads, screen cache, SSH wire, P-256 and the shared worker) run in KelpCore. `npm run check` type-checks `@kelpcore/web` with the application (`tsconfig.json` includes its source), and Vite excludes it from dependency pre-bundling so its `new URL("./session-worker.ts", import.meta.url)` SharedWorker keeps resolving next to it.

Browser-level tests of the `@kelpcore/web` terminal component (WebGL/Canvas renderer, inset geometry, trusted copy events) run with Playwright in Chromium and WebKit and need no network: `node test/renderer.mjs` and `node test/terminal.mjs` in `web/` (the latter also checks that a read-only grid tile claims its pane only to size it, sends no keys, paste, wheel or pointer input, and opens its terminal on a click), plus `node test/app.mjs` and `node test/mobile.mjs` after `npm run build` (the built client boots cross-origin isolated to the sign-in page with its worker and WASM core; ## Relay configuration

Start the workspace with the ordinary launcher (`kelpmux start --workspace main`), make sure OpenSSH accepts key logins for the account, then run the relay with a JSON configuration (see [examples/web-relay.json](../examples/web-relay.json)):

```json
{
  "enabled": true,
  "listen": "127.0.0.1:8080",
  "origin": "https://terminal.example.com",
  "ssh_target": "127.0.0.1:22",
  "ssh_host_key": "ssh-ed25519 AAAA…",
  "username": "alice",
  "bridge_command": "/opt/kelpmux/current/kelpmux web-bridge --workspace main",
  "workspace": "main",
  "dev": false,
  "glitchtip_dsn": null,
  "error_environment": null,
  "idle_warning_minutes": null,
  "idle_lock_minutes": null
}
```

```sh
kelpmux web-relay --config /etc/kelpmux/web.json
```

- `enabled` must be `true`; the relay refuses to start otherwise.
- `listen` is the local address; put a TLS-terminating reverse proxy with WebSocket support in front of it.
- `origin` is the exact HTTPS origin users open. Its host name is also the WebAuthn relying-party ID, so keys registered for one origin do not work on another.
- `ssh_target` is the one SSH destination the relay may reach. `ssh_host_key` is that server's Ed25519 public key (algorithm and base64, from `/etc/ssh/ssh_host_ed25519_key.pub` obtained through a trusted path), not a fingerprint and never a private key.
- `username` is the Linux account; `bridge_command` is the exact command the browser asks OpenSSH to run (use absolute paths: a noninteractive SSH session may have a minimal `PATH`, and shell startup files must not print to standard output). `workspace` names the workspace for display.
- `dev` only adds a DEV badge to the interface.
- `glitchtip_dsn` (optional, default unset) turns on [error reporting](#error-reporting) to a GlitchTip project; `error_environment` (optional, default unset) names the environment events are filed under, such as `preprod`. Without a DSN nothing is reported and the browser loads no reporting code.
- `idle_warning_minutes` (optional, integer 1–1440, default 60) and `idle_lock_minutes` (optional, integer 1–240, default 15) set the [idle lock](#idle-lock): after `idle_warning_minutes` without activity every KelpMux window of a browser shows a warning with a countdown, and if nothing happens within `idle_lock_minutes` more the shared connection locks. Any other value stops the relay at startup. Each one set is handed to the browser in `/connection.json` under the same name; unset (or `null`), the browser uses the default.

Hosting is the operator's responsibility; nothing installs a service. Start with private or VPN-only access.

## Error reporting

Optional and off by default: KelpMux can report errors to a [GlitchTip](https://glitchtip.com) project (self-hosted and Sentry-compatible) with the Sentry SDK. It reports errors and crashes only. There is no performance tracing, session replay, profiling, session tracking or cron monitoring (GlitchTip has none of the last three anyway).

**Components.** The web client reports with the Sentry browser SDK (component `web`). The `kelpmux` executable reports with the official `sentry` Rust crate (see [native.md](native.md#error-reporting)): the relay's own panics and SSH-leg errors (`relay`, from the same `glitchtip_dsn` and `error_environment`), `web-bridge` panics (`bridge`) and TUI panics (`tui`), the last two from `KELPMUX_GLITCHTIP_DSN` and `KELPMUX_ERROR_ENVIRONMENT` in their environment. The relay reports two errors it also logs to stderr, each at most once a minute: `relay.ssh_connect` (the SSH target refused or timed out) and `relay.ssh_handshake` (the target's SSH handshake failed the pinned host-key check), with the OS error or the relay's fixed message as text. It does not report per-request errors such as a wrong origin or a malformed request.

**Configuration.** Set `glitchtip_dsn` in the relay's configuration to the project's public DSN, `https://KEY@HOST[:PORT]/PROJECT_ID`, and optionally `error_environment` (1–64 letters, digits, `.`, `_` or `-`). The relay checks both at startup and refuses an `http://` DSN or one with a secret key, since the DSN is handed to every browser. When a DSN is set, `/connection.json`, the bootstrap document the browser already reads from the relay, gains `"errors": {"dsn": …, "environment": …}`, and the relay adds the DSN's origin (`https://HOST[:PORT]`) to the `connect-src` of its Content-Security-Policy. Without a DSN neither changes, the browser never loads the reporting code (a separate chunk, `assets/error-reporting-*.js`, about 64 kB, 22 kB gzipped) and nothing is sent. Reports are cross-origin `fetch` requests in CORS mode, which cross-origin isolation (COOP/COEP) allows; GlitchTip answers them with the needed CORS headers.

**What is sent.** Uncaught errors and unhandled promise rejections, with their `cause` chain and duplicates dropped, through a bare `BrowserClient` with only those integrations. That means no breadcrumbs (console, DOM, fetch, navigation), no user, IP inference (`infer_ip: never`), cookies, headers, request bodies or query parameters, no client reports, and none of the SDK's default integrations. A `beforeSend` hook additionally removes `user`, `breadcrumbs` and `extra`, reduces `request` to its URL, and strips query strings and fragments from that URL and from every stack frame's file name. Events are tagged `component: web` and carry the build's release and the configured environment. KelpMux never adds terminal content (text, input, titles, folders or commands) as tags, extra data or context. An error message is sent as thrown, so error messages must not include terminal content either.

**Pages and workers.** Every page of the client, popped-out terminals included, starts reporting the same way after reading `/connection.json`. The SharedWorker that holds the SSH connection does not load the SDK: keeping it out of the page that holds SSH transport state is simpler and safer, and the worker's failures already reach the pages that use it, which show them.

**Release name.** `kelpmux@VERSION+SHA`: the version from `Cargo.toml` and the first 12 hex digits of the Git commit, for example `kelpmux@0.2.0-beta.7+c5b489c1a2b3`. Without Git information it is `kelpmux@VERSION`. `KELPMUX_GIT_SHA` supplies the commit when the build has no Git checkout, and `KELPMUX_RELEASE` overrides the whole name (letters, digits, `.`, `_`, `@`, `+`, `-`; at most 200). The web build (`web/scripts/release.mjs`, through Vite's `define`) and the Rust build (`build.rs`, as `kelpmux::native::error_reporting::RELEASE`) compute it the same way, so one build reports one release. When the web build ran without Git (in a container without the repository's `.git`, for example) and the Rust build with it, the two would differ: `build.rs` warns when `web/sourcemaps/RELEASE` names another release. A deploy should set `KELPMUX_RELEASE` (or `KELPMUX_GIT_SHA`) for both builds.

**Source maps.** For each build, the deploy uploads the client's source maps to the GlitchTip project for the release in `web/sourcemaps/RELEASE`, before or when it ships that build. Vite builds them as hidden maps (no `sourceMappingURL` comment) and moves them out of `web/dist`, so the relay neither embeds nor serves them. The browser loads scripts from `/assets/`, so stack frames reference `https://ORIGIN/assets/NAME.js`. Upload, under the URL prefix `~/assets/`:

- each minified script `web/dist/assets/NAME.js` as `~/assets/NAME.js`: `index-*.js` (the application), `error-reporting-*.js` and `session-worker-*.js`;
- its map `web/sourcemaps/assets/NAME.js.map` as `~/assets/NAME.js.map`.

Because the scripts carry no `sourceMappingURL`, the uploader must link each script to its map: `sentry-cli` does so for `NAME.js` and `NAME.js.map` in the same directory. For example, stage both into one directory, then run `sentry-cli --url https://GLITCHTIP sourcemaps upload --release "$(cat web/sourcemaps/RELEASE)" --url-prefix '~/assets' STAGING_DIR`. With another uploader, give each script the artifact header `Sourcemap: NAME.js.map`. Never copy the maps into `web/dist`: `build.rs` skips `*.map` files, but anything else there would be served publicly.

## Registering a YubiKey

1. Open the HTTPS origin. On the sign-in page choose **Register a new key**, then **Register new key**, and touch the key. This creates a discoverable ECDSA P-256 credential with required user verification, scoped to this origin. It grants nothing on its own.
2. Copy the displayed OpenSSH public key (`sk-ecdsa-sha2-nistp256@openssh.com …`) and add it to the account's SSH authorization through your usual mechanism (for example `~/.ssh/authorized_keys`, optionally prefixed with `restrict,verify-required,command="…"` as described above). The web client never edits SSH authorization.
3. Choose **Sign in with security key** and touch the key. When this browser remembers the last key used, one touch signs the login. **Use another security key** (or a new browser) first asks the authenticator which credential to use; because WebAuthn assertions do not return the public key, the browser recovers the candidate public keys from that signature and offers them all to OpenSSH, which asks the server which one is authorized before requesting a second touch to sign. Nothing needs importing on a new browser.
4. If the server accepts none of the candidates, the page says the key is not authorized for the account.

Register and authorize each physical key separately. Settings → Security keys names keys, picks the one used for the next sign-in, shows public keys and exports or imports public registrations; these details stay in this browser. Removing a key there does not delete the credential from the authenticator or revoke its SSH authorization. Removing the SSH authorization stops new logins; it does not end existing SSH sessions.

## Using it alongside the TUI

The TUI and the web client are independent clients of the same KelpServer. You can use the TUI alone, the web alone, or both at once on the same panes and processes:

- Layout is per client. The TUI keeps its grid, tabs, parking, tab colours and focus; each browser keeps its own view mode, terminal order, parked terminals, focused terminal, sidebar width and folding in `localStorage` (layout per workspace, discarded when the server restarts with a new epoch). Neither changes the other's layout. The web client has no tab colours (decision 177); the TUI's colours stay in the TUI, and a layout stored by an older web build with colours still loads, its colours ignored. Parking in the browser hides a terminal from this browser's list and grid only; it keeps running and stays visible in the TUI. Parking in the TUI likewise stays in the TUI: parking is each client's own state, and KelpServer 0.3 reports every pane as unparked.
- Notification read marks are shared. Showing a terminal in the browser marks its notifications read for every client, as the TUI does when it shows one: the terminal shown on its own (or in its popup window). The live grid is read-only and marks nothing read: its tiles keep their bells until their terminal is shown. A notification that arrives for the shown terminal is marked read at once while the browser window is visible and focused; one that arrives while the window is hidden or in the background keeps the bell until the window is looked at again, and a hidden window never marks anything read. The bell in a terminal's header opens its notifications, mainly as a history (**History** by default, with **Unread**, **Mark read** and **Mark all read** too). The TUI's marks show in the browser and the browser's in the TUI. The browser's alerts (in-app toasts, the favicon bell and the optional sound; see [Notifications](#notifications)) are this browser's own preferences (Settings → Notifications).
- Creating or closing a terminal is shared: a new pane appears in every client, and closing one (always confirmed) ends its processes for everyone.
- Input and size follow whichever client last used a pane. When a browser focuses a terminal or types into it, it claims that pane's input and size lease and resizes the PTY to its own view. When the TUI's controlling client then types, pastes, clicks or focuses that pane, the TUI takes it back and the pane returns to the TUI's geometry. The live grid is a foreground layout too: while the browser window is focused and visible, it sizes each tile's pane to that tile (claiming it), so opening the grid in a browser resizes the panes it shows until the TUI uses them again. A tile claims the lease only to size its pane: the grid has no focused tile and sends no keyboard, mouse, paste or touch input, and no keyboard action addresses a tile. Passive rendering in a background window, mouse movement, window blur and focus-out never take a pane. Each pane has exactly one PTY size; a client that does not hold the lease shows the pane clipped or padded. Different panes can be held by different clients at the same time.
- The focused terminal's header shows a **TUI** or **Other browser** badge while this browser does not hold its input and size (hover it for details). Closing the browser or losing the connection releases its leases; terminals keep running and return to the TUI's geometry.
- Only one TUI client is the controller (input and workspace size); further TUI clients are observers, as before. Web clients are not TUI controllers or observers and do not affect that role.

Other same-origin tabs and **Open in a window** popups reuse the SSH connection held by the first tab through a SharedWorker; keep that tab open. **Log out all browser windows** (Settings → Connection) or `Ctrl-B d` closes SSH for every window of the browser; workspace processes keep running.

## Notifications

The browser alerts with in-app toasts in the top right corner of the app, at the top of the one toast stack (download progress and confirmations such as "Path copied" follow below them, newest first, so the toasts never overlap; on a phone the whole stack is full width under the terminal bar); it no longer uses the browser's desktop notifications (Web Notifications API) or asks for their permission (owner decision, 2026-11-22). A toast appears for each new workspace notification of an enabled event: **Question** (input needed), **Finished** (a turn finished), **Failed**, **Exited** (an agent exited) and **Bell** (an agent rang the terminal bell), the TUI's event names (`notification_events`). KelpServer records these events for agents only. Notifications already there when the browser connects make no toast.

- **One toast per terminal.** A new event of a terminal that already has a toast updates that toast (its newest event, raised to the top) instead of adding one. A bell that accompanies a typed event (same terminal and process, within two seconds) shows as that event, so a question with its bell makes one toast; KelpCore will later merge the two on the server.
- **More than three toasts collapse** into one summary ("5 terminals need attention"); a click expands it into the list of terminals.
- **Clicking a toast** or a summary entry opens its terminal exactly as choosing it in the sidebar does: shown alone (leaving the grid, unparked if parked), or opened full screen on a phone. Showing it marks its notifications read, which removes the toast.
- **No toast for the terminal being read**: the terminal shown alone, while the window is visible. The read-only grid has no focused terminal and marks nothing read, so every grid tile gets toasts, as it keeps its bell. Popup windows show no toasts; their main window does.
- **Toasts go when read anywhere**: when the terminal's notifications are marked read in this window, another browser window or device, or the TUI (read marks are KelpServer's workspace state, shared by every client), when the terminal or its process ends, or when the event is turned off. They have no timer. The close button only hides a toast; the terminal's notifications stay unread and its bell stays in the sidebar.
- **Favicon bell.** While an unread bell remains, the browser tab's icon gets an amber dot in its top right corner, removed when the bell is read. It follows the Bell event setting.
- **Phones.** Toasts span the width minus the 16 px gutters, below the safe area and the terminal bar, away from the key bar at the bottom.

Settings → Notifications has one toggle per event, all on by default like the TUI's, and the sound (off by default), which plays for the same enabled events. These preferences are stored per browser (`notificationEvents` in `kelpmux-web-preferences`); the former **Desktop** choice stored by earlier builds is ignored and dropped on the next save.

## Idle lock

The shared connection locks when nobody uses it (decisions 163–165). After 60 minutes without activity in any KelpMux window or popup of the browser, every window shows a warning with a live countdown ("KelpMux locks this connection in 14:59. Your shells keep running.") and a **Stay signed in** button. Any activity in any window, the button included, lifts the warning in every window; if nothing happens within 15 more minutes, the connection locks for every window, which then shows the sign-in page with the reason. Shells and jobs keep running; signing in with the security key reconnects. Both durations can be changed in the [relay configuration](#relay-configuration) (`idle_warning_minutes`, `idle_lock_minutes`).

- **Activity** is a key press, a click or tap, a touch or scrolling anywhere in a KelpMux window, and terminal input, paste, mouse reporting, uploads and deliberate actions as before. Terminal output, mere pointer movement, background polls and window heartbeats do not count. Each window reports its activity to the shared worker at most once every 30 seconds (at once while the warning is shown).
- **Wall-clock deadlines.** The shared worker checks the deadlines with timers, every 10 seconds and before handling any message from a window, against the clock rather than elapsed timer time. A browser that throttled or suspended the worker (background tabs, a sleeping laptop, a phone with the screen off) locks as soon as it wakes if both durations have passed, without showing the warning first; the first key press after waking cannot revive the connection.
- Without SharedWorker support (each window then holds its own SSH connection) there is no idle lock.

## Uploads

Files and images dropped onto a terminal are uploaded to the host where its shells run, and their paths are pasted into that terminal, through KelpServer's `uploads` stream capability (decision 151a; see the [KelpServer protocol](https://github.com/joanfabregat/kelpcore/blob/main/crates/server/docs/native-client-protocol.md#uploads-uploads)). The [file browser](#files) can also upload files dropped onto a folder into that folder.

- **Drop targets.** Drop one or more files or images onto the terminal shown on its own (the read-only live grid takes no drops). Pasting an image (a clipboard with files and no text, such as a screenshot) into a terminal does the same. Every terminal's menu (right-click, or **⋯** on phones and tablets) also has **Upload files…**, which opens the system file picker, so iPhones and iPads, which have no drag and drop onto a page, can upload too. Files dropped elsewhere on the page are ignored rather than opened by the browser.
- **Dialog.** Nothing is sent until the upload dialog is confirmed. It shows the target terminal, each file's name and size, the total and the destination folder. Folders cannot be uploaded: a dropped folder is listed as skipped. The server's advertised Welcome `upload_limits` are enforced before anything is sent (64 files, 100 MiB per file and 1 GiB per drop by default); a drop over a limit explains which one and cannot be started.
- **Destination.** By default each drop gets its own new private folder in the server's upload folder (`~/.cache/kelpserver/uploads` unless the server is configured otherwise with `kelpmux start --upload-dir`; KelpServer deletes completed uploads there after its retention, 7 days by default, set with `--upload-retention-days`; see [native.md](native.md#named-workspaces)). Settings → **Uploads** sets a default destination folder instead: an absolute path on the server host, which must be an existing folder owned by the account (KelpServer checks this), sent as `dest`; each drop then gets its own private folder inside it. The setting is kept in this browser only. The dialog can change the folder for one drop, with **Remember as the default destination in this browser**.
- **Progress and cancel.** The dialog shows each file's progress and the total. The client sends chunks of at most 128 KiB (or the server's smaller `max_chunk_bytes`) and never has more than the server's `max_chunks_in_flight` unacknowledged on the connection; windows sharing one SSH connection share that window through the SharedWorker, which also routes each upload's events to the window that began it and cancels the unfinished uploads of a window that closes. **Cancel upload** sends `upload_cancel`, and the server removes the batch with its partial files. A refusal (a missing or foreign destination, too many uploads at once, not enough space) or a failure is shown in the dialog, and nothing is pasted.
- **Paste.** When the upload is done, the absolute paths are quoted for POSIX shells (`'…'`, with `'` written as `'\''`, unless a path only has safe characters) and pasted, space-separated, into the terminal the files were dropped on, as a paste: bracketed when the program has bracketed paste on, and without Enter, so nothing runs until you press it. Pasting takes the terminal's input and size, as typing does. If that terminal closed during the upload, the dialog lists the paths with copy buttons instead.
- **Requirements.** The server must offer the `uploads` capability and the bridge must report `uploads` in its operations (API 3, minor 1); otherwise a drop opens the dialog with the reason (restart the workspace with a current KelpServer, or install matching KelpMux versions) and sends nothing.

Uploading is the same trust as typing into a shell: anyone signed in can already write any file the account can write. The paths come from the server and are checked by the WASM core (absolute, no control characters) before they can be pasted.

## Files

The **Files** header in the sidebar opens a file browser of the server user's files, rooted at the home folder, in the main area; files open from it in a text editor in the same place. The Files section itself lists the home folder as a tree, with the same menu, drags and drops as the browser (see [Layout](#layout)). Both use KelpServer's `files` stream capability ([KelpServer protocol](https://github.com/joanfabregat/kelpcore/blob/main/crates/server/docs/native-client-protocol.md)) on the existing SSH connection; the bridge relays the requests and replies unchanged (API 3, minor 2). The browser and editor components, the request client and the CodeMirror editor are KelpCore's `@kelpcore/web/files/` (derived from KelpHub's); KelpMux supplies the views, the sidebar entry and the wiring.

- **Browsing.** Folders first, then files, by name in natural order; size and modification time on each row (under the name on phones). Hidden entries (names starting with `.`) show only after the eye button, a choice kept in this browser. Breadcrumbs (Home for `~`), the parent folder, **Refresh**, **New file** and **New folder** sit above the list. Clicking a folder opens it, clicking a file opens it in the editor; a symbolic link opens what it points to. Each terminal's header has a folder button (and its menu **Browse files here**) that opens the browser at that terminal's current folder.
- **Operations.** Each row's **⋯** button (or a right-click) has **Open**, **Insert path into terminal N** (the terminal last shown alone), **Copy path**, **Download** (a folder: **Download as .tar.gz**; see below), **Rename…** (inline), **Move to trash** (the freedesktop trash, `$XDG_DATA_HOME/Trash`, as file managers use; a file on another file system than the trash must be deleted instead) and **Delete permanently…**, which asks first. Dragging an entry onto a folder row or breadcrumb moves it there. Open editors follow renames and moves; trashing or deleting closes the unchanged editors inside and leaves changed ones open with a note.
- **Paths into terminals.** Dragging an entry onto a terminal's sidebar row, or onto the terminal shown, types its path into that terminal, quoted for POSIX shells as uploads paste theirs, as a paste and without Enter. A path with control characters is refused rather than typed.
- **Uploads into a folder.** Files dropped from the desktop onto a folder row, a breadcrumb or the list upload into that folder (the **Upload** button opens the file picker), with progress and Cancel above the list. KelpServer puts each upload in a private batch folder inside the destination; the browser then moves each file out of it into the folder and removes the empty batch folder. A name already taken in the folder keeps its file in the batch folder, and the message names it. Files dropped onto a terminal still upload as described in [Uploads](#uploads).
- **Downloads.** **Download** in a file's menu, or the download button in the editor's header, saves the file to this computer; **Download as .tar.gz** in a folder's menu saves the folder and everything in it as one gzip-compressed tar archive named after it. KelpServer streams the bytes in chunks the browser acknowledges once written (`file-downloads`, KelpCore's `saveDownload`), so a download never fills the connection or holds back terminal output. Where the browser has the File System Access API (Chromium), the save dialog comes first and the bytes go straight to the chosen file; elsewhere they are collected in memory, up to 1 GiB, and handed to the browser's downloads at the end. A progress toast in the top right toast stack (below the [attention toasts](#notifications), above the confirmations) shows each running download with **Cancel**, which stops it on the server and discards the partial file. Archives keep symbolic links as links, never follow them, stay on the folder's file system, keep permission bits and modification times (no owners), and leave out special files and unreadable entries (counted in the final notice); a folder over the server's entry or size bounds is refused before anything is sent. The editor downloads the saved file, not unsaved edits. Without the `file-downloads` capability, or with a bridge older than API 3.3, there are no Download actions.
- **Editor.** CodeMirror 6 with syntax highlighting chosen from the file name, search (`Ctrl/Cmd+F` inside the editor), line numbers and the app's theme colours; it is loaded only when the first file opens. Open files are listed under **Open** in the sidebar's Files section, each with a dot while it has unsaved changes and a close button, and marked in its tree; each open file keeps its editor, with any unsaved changes, while a terminal, the grid or another file shows; closing a changed file asks first, and the page warns before unloading while any file has unsaved changes. **Save** (`Ctrl/Cmd+S`) writes with the hash the file was read at: if the file changed on disk since, a dialog offers **Reload** (discarding the edits), **Overwrite** or **Cancel** (keep editing). Binary files and files larger than the server's `max_read_bytes` (8 MiB by default) show an information view instead. Text files larger than 2 MiB (the largest single write the browser sends through the bridge) or the server's `max_write_bytes` open read-only.
- **Side panel.** A file can also open in a panel docked to the right of the terminal shown alone: **Open beside terminal** in a file row's menu opens it beside the terminal last shown alone and switches the main area to that terminal, and the editor's **Move beside terminal** button moves a file shown in the main area there (the panel's own button, **Open in the main area**, moves it back). There is one side panel per window, showing one file with the editor's usual header (name, folder, dirty dot, Save, Reload, Show in folder, Close); the file is also listed under the Files entry, and clicking it there shows the terminal with the panel. Opening another file in the panel replaces the one shown, which stays open in the list (one with unsaved changes is closed after asking). It is the same editor and document as in the main area: `Ctrl/Cmd+S` saves while the focus is anywhere in the panel, conflicts offer the same Reload, Overwrite or Cancel, and the panel's Close closes the file (asking first when it has unsaved changes). A file moves between the main area and the panel only without unsaved changes (save first), because the buffer lives in the mounted editor. Dragging the panel's left edge resizes it; the width is kept in this browser like the sidebar's, and the terminal always keeps at least 240 pixels. The terminal re-fits its columns and rows when the panel opens, closes or is resized. Clicking the terminal gives it the keyboard; clicking the editor gives it to the editor. The panel hides while the grid, the file browser or an open file in the main area shows and reappears, with its unsaved edits, beside the terminal shown alone.
- **Path links.** With Cmd or Ctrl held, a file path printed in the terminal shown alone becomes a link: hovering it underlines it and shows a pointer, and clicking opens a file in the side panel at its line and column, or a folder in the file browser. Nothing is scanned in advance. At the cell under the pointer the client takes the token from that row's text: the text between quotes when the pointer is inside a quoted span (which may hold spaces), otherwise the run of non-space characters, without leading brackets or quotes and trailing punctuation (`.,:;)]}>` and quotes). It accepts `path`, `path:line` and `path:line:col`, `./rel`, `../rel`, `~/x`, absolute `/x` and bare relative names, resolved against the terminal's current folder; URLs (`scheme://…`) and tokens of only dots, slashes and tildes are not paths. Only something that exists is a link: a `file_stat` request, sent once the pointer rests for 80 ms and remembered for five seconds, decides it. An OSC 8 hyperlink keeps its own behaviour: an `http(s)` one opens on any click, Cmd/Ctrl included, and a `file://` one is used as the path. The click is taken before the terminal's own handling, so it neither starts a selection nor reaches an application that turned mouse reporting on; every other click, drag and wheel event, with or without the modifier, behaves as before. A path wrapped across two rows is not joined (the screen model carries no soft-wrap marks), terminal history scrolled back has no links, and neither do grid tiles or popup windows. The parsing is `web/src/files/path-links.ts`, pure functions with unit tests, which could move to `@kelpcore/web`.
- **Phones.** A phone has no side panel: **Open beside terminal** opens the editor full screen, as **Open** does, and the editor has no move button.
- **Requirements.** The Files entry shows only when the server's Welcome lists the `files` capability with `file_limits` and the bridge reports `files` in its operations. Without them there is no side panel, no **Open beside terminal** item and no path links.

Like uploads, the browser and editor are the same trust as a shell: anyone signed in can already read and write any file the account can. KelpServer resolves `~` and enforces its own limits (entries per listing, paths per request, requests in flight, read and write sizes) and refuses to remove `/` or the home folder.

## Layout

On a desktop or tablet the left sidebar is the only navigation; there is no top bar and no status bar. The main area shows the focused terminal (with the [side panel](#files) to its right when a file is open there; its header has the number, state, title, folder, a **TUI** or **Other browser** badge when that client holds its input and size, and the files button, notifications bell, Find, Park, Open in a window and Close), the live grid, the file browser or an open file. From top to bottom the sidebar holds:

- KelpMux, the **DEV** badge on a development relay, and the state counts (click one to jump to the next terminal in that state), with no separator line before the tabs.
- Two collapsible sections, **Terminals** then **Files**. Each header is a row like a tab's, with its icon (a 2×2 grid for Terminals, a folder for Files; only the icon when the sidebar is folded), and two separate targets: clicking the label opens the section's view and a chevron at its right end expands or collapses the section (a button with `aria-expanded`, so `Enter` or `Space` toggles it from the keyboard). A header is selected while its view shows. Collapsed, a header keeps the number of entries it hides and a dot while one of them needs attention, so collapsing never hides an alert. Each section's state belongs to this browser (stored with the sidebar preferences; both start expanded); the folded rail ignores it and shows every tab.
- **Terminals**: its label opens the live grid (phones have no grid: there the whole header expands or collapses the list). Its collapsed count is the number of open terminals, and its dot shows while any terminal, parked ones included, needs input, has failed or has unread notifications. Under it, the terminal tabs in this browser's order. Clicking a tab opens that terminal alone, also from the grid; the tab of the terminal shown alone is selected, and in the grid no tab is (the Terminals header is). The grid is one read-only page for monitoring: it shows every live (unparked) terminal at once, in columns and rows chosen to fit them all in the available area with tiles close to a terminal's shape, re-laid out as terminals come and go, with no paging. It has no focused tile and takes no input; each tile shows its terminal's state, badges, unread bell, title and folder above its live screen, and a click anywhere on a tile opens that terminal alone. The headers and the tabs look alike, with no colour stripe; a thin rule separates each terminal from the next, and there is none under the section headers (spacing separates the sections). **New terminal** follows right under the tabs, like the TUI's "+ New tab" row: a row like a tab, its **+** in the number column and its label muted until hovered (only the **+** when folded); its tooltip gives the shortcut, `Ctrl-B Enter`. Then the collapsible **Parked** subsection. A tab with unread notifications that is not shown alone shows a ringing bell (with the count when there are several), as does its grid tile header.
- **Files**, when the connection offers files: its label opens the [file browser](#files). Under it, the collapsible **Open** subsection (like Parked) lists the files open in the editor, each with a dot while it has unsaved changes and a close button on hover; clicking one shows it. Then the home folder as a tree, listed the way the terminals are: rows with an icon and a name, folders first, hidden entries only when the file browser shows them. Clicking a folder's row expands it in place (a chevron in the number column; it is listed when expanded, and again each time it is expanded) and clicking it again collapses it; clicking a file's row opens it in the main area as a terminal's row opens the terminal, and the row of the file shown is selected. Open files are marked in the tree (a grey dot, amber while unsaved). Each row has the file browser's menu (right-click, or **⋯** on hover and always on touch devices): **Open** (a folder opens in the file browser), **Open beside terminal**, **Insert path**, **Copy path**, **Download**, **Rename…** (inline), **Move to trash** and **Delete permanently…**. A row dragged onto a terminal's row or view types its path; dragged onto a folder's row it moves there; files dropped from the desktop onto a folder's row (or onto a file's row: its folder) upload into that folder. Changes made in the tree or the browser list the touched folders again in both. Which folders are expanded is kept in this browser. Collapsed, the section shows the number of open files and a dot while one has unsaved changes. The folded rail shows the open files only. A long tree scrolls with the rest of the sidebar: Terminals come first, so the tree never pushes them away, and one scrolling list avoids a second, nested scroll area.
- The vitals, drawn like the TUI's sidebar status: CPU (green) and RAM (purple) meters with their percentages, then the first two disks as pies filled by usage like the TUI's `○ ◔ ◑ ◕ ●` (yellow, red from 90 % used), each with its mount point and percentage in a tooltip. The colours are the TUI's in dark mode and darker shades of the same hues in light mode. Clicking the vitals opens System status.
- The tools in two columns, like the TUI's sidebar buttons, with short labels: **Terminals** (with a list icon, unlike the Terminals header's grid icon), **Closed** (Recently closed), **Search** and **Help**. Each tooltip gives the full name and shortcut. They scroll on their own when the window is short, so the tabs keep most of the height; with ten tabs they fit an 800 pixel tall window without scrolling.
- At the very bottom, the account (the user name) and its **Settings** (`Ctrl-B ,`).

A narrow fold handle sits vertically centred on the sidebar's edge; the folded rail keeps the numbers, state marks and unread bells, the tools' icons in one column, compact vitals (CPU and RAM percentages and the disk pies) and the account's initial. Clicking the edge also folds it and dragging it resizes. There is no full width mode: the folded rail is the smallest sidebar. The workspace name is not shown anywhere in the main interface: one relay serves one workspace, so the sign-in screen names the user and the relay's host instead, the **Workspace not running** screen names the workspace it would start, and Recently closed names a workspace only on an entry that came from another one.

## Keyboard

`Ctrl-B` is the browser's prefix, and the keys after it follow the TUI's default bindings wherever the browser has the same action: `Enter` new terminal, `Tab`/`Shift+Tab` next/previous terminal, `1`…`9` terminal by number, `g`/`e` live grid, `h`/`k` or left/up arrows previous terminal and `j`/`l` or right/down arrows next terminal, `N` next question, `P` next completion, `o` the Terminals table, `a` the same table showing agents, `!` agents needing attention, `n` finished agents, `b` the focused terminal's notifications, `r` recently closed, `z` reopen the last closed terminal, `/` search terminal history, `[` scroll mode, `Space` selection mode, `p` park, `u` parked terminals, `s` move, `x` close (confirmed), `,` settings, `?` help, `d` disconnect, and `Ctrl-B` twice sends `Ctrl-B` to the terminal. Every key that opens a terminal (a number, next or previous, next question or completion, reopen) shows it alone, leaving the grid; in the read-only grid the keys that act on the focused terminal (`b`, `[`, `Space`, `p`, `s`, `x`, `Ctrl-B` twice, `Ctrl/Cmd+F`) do nothing. Outside the prefix, `Alt+1`…`Alt+0` open terminals 1–10, `Alt+Tab` or `Ctrl/Cmd+Shift+G` toggle one terminal / live grid, and `Ctrl/Cmd+F` finds in the focused terminal. In scroll mode, `PgUp`/`PgDn`, `Ctrl-U`/`Ctrl-D`, `Ctrl-B`/`Ctrl-F`, `j`/`k` or arrows scroll, `g`/`G` jump to the oldest line or the live screen, `Space` or `v` switches to selection, and `Esc` or `q` leaves. In selection mode, `h`/`j`/`k`/`l` or arrows move the cursor (scrolling at the edges), `0`/`$` line start and end, `w`/`b` eight columns, `Space`/`v` set or clear the anchor, `y` or `Enter` copy and leave, `Esc` or `q` leave. Every other key goes to the terminal shown on its own (never to a grid tile) with full modifier and Kitty keyboard-protocol support. Settings → Keyboard and Help list these bindings. The TUI's own bindings and configuration file are unchanged; custom TUI bindings are not read by the browser.

The mouse covers the rest: click a sidebar row to open that terminal alone or the **Terminals** header's label to open the grid (its chevron expands or collapses the section), click anywhere on a grid tile to open that terminal alone, drag rows (or grid tiles) to reorder, right-click a row or tile for its menu (open, open in a window, find, move up/down, park/unpark, notifications, upload files, browse files here, close), drop files onto the terminal shown on its own to upload them, Cmd/Ctrl-click a file path printed in it to open the file beside it ([path links](#files)), middle-click a row to close it, click the sidebar's state counts to jump to the next terminal in that state, click the fold handle or the sidebar's edge to fold it, and drag the edge to resize it.

## Navigation

The page URL names the place shown, so the browser's Back and Forward (its buttons, a mouse's back and forward buttons, `Alt+←`/`Alt+→` outside a terminal that takes them, a two-finger swipe on a Mac, a phone's back gesture) move through the places visited, and a reload, a bookmark or a link opens the same place. Everything stays in one page: Back and Forward never reload it and never leave a terminal's session. `web/src/navigation.ts` encodes, decodes and decides; `main.tsx` mirrors its state into the history after every change and applies the location of each `popstate`.

| Place | URL query |
| --- | --- |
| One terminal on its own | `?view=terminal&terminal=<pane id>` |
| …with a file in the [side panel](#files) | `?view=terminal&terminal=<pane id>&side=<path>[&line=<n>]` |
| The live grid | `?view=grid` |
| The file browser at a folder | `?view=files&dir=<folder>` |
| An open file in the main area | `?view=files&file=<path>[&line=<n>]` |
| A phone's terminal list | `?view=home` |
| A panel over any of them | `…&dialog=<settings, help, terminals, search, closed, parked, move, status or notifications>[&of=<pane id>]` |

A terminal is named by its server pane id, which stays the same while terminals are reordered, parked or renumbered, never by its position. Paths keep `/` and `~` readable and escape the rest. `of` is the terminal whose notifications the panel shows; `line` is where the file opened (from a path link). Parameters the client does not own are kept: KelpHub-era links keep `project`, `workspace` and `scratch`, and their `view=terminals` (with or without `terminal`) opens that terminal or the grid, `view=files` the browser, and `view=overview` or `view=events` the client's own default. `pane` is reserved for windows opened with **Open in a window**, which show one terminal and keep no history; each window or tab has its own history, and the shared connection is unaffected.

Which changes add an entry:

- **Push**: every move to another place, whether from the sidebar, a grid tile, a toast, a panel's list or a keyboard shortcut (`Ctrl-B` digits, `Tab`, `g`, `N`, `Alt+digit`, `Alt+Tab`, …), and opening a panel that covers the application (Settings, Help, Terminals, Search, Recently closed, Parked, Move, System status, a terminal's notifications), so Back closes it, as phones expect. Each folder opened in the file browser is a place.
- **Back instead of push**: closing a panel (its close button, `Esc`, a click outside) returns to the entry under it rather than adding one, so the panel can be reopened with Forward and Back never shows the same place twice. Leaving a panel for another place (a terminal opened from the Terminals table or Search) takes the panel's entry, so Back returns to where the panel was opened.
- **Replace**: the first location after loading or reconnecting, a panel swapped for another, another line in the same file, and changes nobody asked for: a terminal that closed or was parked while shown (its next terminal takes the entry), the browser's `~` or a symbolic link read as its real folder, a file closed, a phone turned into a tablet layout, and every fallback below.
- **Nothing**: selecting the place already shown, and everything transient: menus, tooltips, toasts, the find bar, confirmations, the upload review, security key prompts, scrolling, selections and Settings' own sections.

A loaded URL is applied once the client is signed in, the terminals are listed and the files capability is known; until then the URL is left untouched. A terminal that no longer exists falls back to the grid (a phone's list) with a toast, a file that no longer exists to its folder in the browser, a folder to the browser at it, files on a connection without them stay where the client is; each fallback replaces the entry. Going back to a place whose terminal has since closed falls back the same way. A file with unsaved changes in the side panel stays there when Back or Forward goes to a place without it (its buffer lives in the panel's editor); a file without changes moves to the list of open files. Each entry's `history.state` carries `{ kelpmux: { v: 1, overlay } }`: `overlay` marks a panel pushed over the entry below, and the version lets a later format migrate older entries (the URL alone is enough to restore a place).

## Phones and tablets

The same client adapts to iPhone and iPad (Safari first; [ADR 0003](adr/0003-web-client-in-kelpmux.md#addendum-phones-and-tablets) records the decisions). The layout follows the viewport and the primary pointer (`web/src/device.ts`): a touch screen whose short side is under 600 CSS pixels is a **phone** (every iPhone, both orientations), any other touch screen a **tablet** (every iPad), and a mouse-driven window narrower than 600 pixels also gets the phone layout.

- **Phone.** The home screen is the terminal list: the sidebar's content (state counts, the Terminals section with its terminals, **New terminal** and parked terminals, the Files section with its open files and tree, then the vitals, the tools in two columns and the account with settings) at full width, scrolling as one list. Tapping a terminal opens it full screen; **‹ Terminals** returns to the list, the bell opens the terminal's notifications (ringing, with the count, while some are unread), and **⋯** opens the terminal's menu (find, move, park, notifications, upload files, browse files here, close). There is no grid: the **Terminals** header only expands or collapses the list. **Files** in the list opens the file browser full screen, and a file opened from it or from the tree the editor, each with **‹** back to the list. The terminal shown is sized to the phone through the normal per-pane lease, exactly as a desktop browser's focused terminal is.
- **Tablet.** The desktop layout, sidebar and grid, with larger tap targets. Landscape and portrait are both supported; in portrait the sidebar starts folded each time the tablet turns to portrait (that fold is not saved), and the fold handle on the sidebar's edge unfolds it. Landscape uses the saved sidebar preference.
- **Touch on a terminal.** A tap selects the terminal and takes its lease without showing the keyboard (an application that requested mouse reporting receives the tap as a click; a link opens). One finger dragged up or down scrolls the history, as the wheel does. A long press selects the word under the finger; dragging extends the selection, and lifting copies it. Pinch zoom is not supported. Sidebar rows scroll on touch instead of reordering; their **⋯** menu has Move up / Move down.
- **Keyboard.** Opening a terminal never brings up the on-screen keyboard: reading is the default. The key bar under the terminal has **Input**, which shows the keyboard (and becomes a hide-keyboard button while it is up); tapping any key on the bar also enters input mode. The bar holds Esc, Tab, Ctrl, the arrows, `^B`, Paste, Enter, Yes and No. Ctrl is sticky: it applies to the next key from the bar or the keyboard, then releases. `^B` arms the KelpMux prefix, so the next key typed is a prefix key as on a desktop. Paste reads the clipboard (Safari asks first). Yes and No send `1` and Escape to Claude Code, whose questions are numbered menus, and `y` and `n` to anything else; they do not add Enter. The bar follows the `visualViewport`, so it stays directly above the iOS keyboard, and the layout respects the safe-area insets. These rules apply to the iPad too.
- **Hardware keyboard.** Settings → Keyboard → **Hardware keyboard** (shown on touch devices, saved per browser) chooses how a physical keyboard (an iPad's Magic Keyboard, a Bluetooth keyboard) reaches the terminal shown. **Auto**, the default: terminals still open for reading, and the first key typed on a hardware keyboard enters input mode and is delivered to the terminal, not lost. **On**: terminals open in input mode, ready for the hardware keyboard, without bringing up the on-screen keyboard. **Off**: tap Input or a key bar key first, as before. A hardware key is recognised because iPadOS sends it to the page while no text field has focus, which the on-screen keyboard cannot do; Cmd shortcuts, modifier keys pressed alone and the app's own shortcuts (`Ctrl-B` and the others) are left alone. Input mode entered from the hardware keyboard focuses the terminal's input with `inputmode="none"`, so iOS does not show the on-screen keyboard; the Input control and the key bar still show it. With On, Safari may refuse to focus the input when the terminal opens without a tap; the first key typed then enters input mode as with Auto. The setting applies to phones too.
- **Installable web app.** `manifest.webmanifest` (standalone display, theme colours, 192 and 512 pixel icons, a maskable icon) plus the iOS meta tags and a 180 pixel `apple-touch-icon` let Safari's **Add to Home Screen** install KelpMux as its own app. There is no service worker: nothing is cached offline (the client needs its relay anyway), and the cross-origin-isolation and asset headers stay exactly as the relay sets them. There are no push notifications. The PNG icons are rendered from `web/public/icons/icon.svg` by `web/scripts/render-icons.mjs` and committed.
- **Sign-in** is the same YubiKey WebAuthn flow, over NFC or USB-C; iCloud Keychain passkeys are not supported as SSH keys. The sign-in and key-registration screens fit a phone and scroll instead of overflowing.

## Reusable terminal component

The terminal layer is KelpCore's [`@kelpcore/web`](https://github.com/joanfabregat/kelpcore/tree/main/web) package, moved there from this repository's `web/src/terminal/` at `7179aa3` ([KelpCore ADR 0003](https://github.com/joanfabregat/kelpcore/blob/main/docs/adr/0003-kelpcore-shared-repository.md)). KelpMux and another web application (KelpHub) consume it at a pinned KelpCore commit: SSH/WebAuthn connection and key discovery, the SharedWorker session broker, WASM client-core loading, the WebGL/Canvas renderer, keyboard, mouse and wheel encoding, the touch key bar encoding and input mode (`touch-keys.ts`), the upload protocol, limit checks and path quoting (`uploads.ts`), selection and copy, the screen cache, grid column layout, the `Terminal`/`TerminalTile` React components and pane find. It imports no application code. It is not published to an npm registry: `web/package.json` depends on `"@kelpcore/web": "github:joanfabregat/kelpcore#<commit>"`, a TypeScript source package whose files are imported with their extension (`@kelpcore/web/Terminal.tsx`, `@kelpcore/web/terminal.css`; its `exports` maps `./*` to `web/src/*`). Its `files/` modules hold the file request client (`api.ts`), path helpers (`paths.ts`), the open-document model and language detection (`model.ts`, `languages.ts`) and the lazily loaded CodeMirror 6 `TextEditor` with its theme (`editor.tsx`, `theme.ts`), derived from KelpHub's; their CodeMirror and Lezer packages are dependencies of `@kelpcore/web`, so KelpMux gets them through it. Pin the same KelpCore commit as the `Cargo.toml` revision that builds `client-core.wasm`.

## Current limits

- The file browser and editor edit one file at a time per view: no multi-select, split editors, diff, or file search across folders. Text files over 2 MiB open read-only; moving or renaming across file systems, and trashing a file on a file system other than the trash's, fail with the server's reason (delete instead).
- The grid shows every live terminal on one page. It streams as many terminals as the server allows one connection (Welcome `limits`, 64 with `stream-limits`, ten before), less two kept for popup windows; with an older server, tiles beyond that show their header without content.
- Panes cannot be renamed or split from the web: KelpServer has no rename operation, and its layout is automatic. Pane titles follow the running program.
- History search uses the server's bounded literal search (64 matches per terminal); the Search dialog searches at most 32 terminals and shows at most 200 hits. Older history pages are plain text.
- Restoring a closed terminal from the browser does not remove it from the TUI's Recently closed list (the server owns that file); restoring an agent conversation that is already open opens the existing terminal instead.
- Notification state for a pane is matched by pane and process ID; the browser does not see the server's run identifier, so a notification from a previous server run whose pane and process IDs both recur could be shown until it is read.
- Real hardware-key and Safari behaviour need manual acceptance; automated tests use virtual authenticators only where noted.
- Phones and tablets are tested with Playwright device emulation only. The on-screen keyboard, the key bar's position above it, safe areas, Add to Home Screen, NFC and USB-C security keys and the connected phone and tablet layouts need acceptance on a real iPhone and iPad. On iOS an installed web app has its own storage, separate from Safari's: its first sign-in asks the authenticator which key to use, as a new browser does, and its layout and settings start fresh. Closing it, or iOS suspending it in the background, ends the SSH connection like closing a tab; terminals keep running.
