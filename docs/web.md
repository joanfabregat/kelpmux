# Web client

KelpMux includes an optional browser client for the same persistent workspaces as the TUI. It is centred on terminals, with the TUI's feature set adapted to the browser (see [Feature parity with the TUI](#feature-parity-with-the-tui)): a left sidebar of terminals with agent state, a read-only live grid for monitoring, parking, a Terminals table (every terminal with its agent state, folder, Git repository and branch, running program and last activity), per-terminal notifications, recently closed terminals, search, selection and copy, links, keyboard scroll and selection modes, [file and image uploads](#uploads) dropped onto a terminal, a [file browser and text editor](#files) for the server user's files, settings for appearance, alerts, keyboard shortcuts, uploads and security keys. It groups terminals into [projects](#projects) (a name and a folder). Its only Git view is a read-only [Repos view](#repos) per project (branch, upstream, changed files, last commit); Git operations (commit, push, fetch, diffs, history) belong to KelpHub. (The Terminals table only shows, read-only, which repository and branch a terminal's folder is in, with a link to GitHub.) [ADR 0003](adr/0003-web-client-in-kelpmux.md) records why it lives here and what it must not become.

The browser signs in with a hardware security key (WebAuthn) and runs OpenSSH itself, compiled to WebAssembly. The SSH session ends in the browser; nothing on the server side ever holds the session keys or a private key.

## Components

```text
browser ── HTTPS + WSS ──▶ kelpmux web-relay ── TCP ──▶ sshd ──▶ kelpmux web-bridge ──▶ workspace socket ──▶ KelpServer
 (React UI, OpenSSH/WASSH,      (static assets,              (user's          (stdio, same-user        (PTYs, emulation,
  WASM terminal core)            byte relay)                  account)         peer check)               processes)
```

- `web/`: the React/TypeScript browser client. The reusable terminal pieces come from KelpCore's `@kelpcore/web` package (see [Reusable terminal component](#reusable-terminal-component)); `web/src` is the KelpMux application shell around them.
- `kelpclient` (KelpCore's `crates/client`, a Git dependency), compiled to `wasm32-unknown-unknown` and served as `client-core.wasm`: stream framing, validation, history layout and selection shared with native Rust clients.
- KelpServer and `kelpclient` come from the [KelpCore](https://github.com/joanfabregat/kelpcore) repository at the revision pinned in `Cargo.toml`, so `client-core.wasm` is built with `kelpclient-protocol` from the same revision as the server; `@kelpcore/web` in `web/package.json` pins the same KelpCore commit. KelpMux requires KelpServer 0.3 or later, which speaks only the pane stream (no composed protocol 58) and starts a workspace without panes: the first client creates them. The web relay is KelpMux's own (`src/native/web_relay.rs`); KelpServer removed its copy in 0.3.0-beta.2. Since that release (`kelpclient-protocol` 0.3.0) the pane list has no `number` or `parked`: the browser numbers terminals by their position in its own order (`numberPanes` in `web/src/layout-store.ts`), so without a stored order the numbers are the creation order, as before, and it keeps parking in its layout store.
- `kelpmux web-relay --config PATH`: serves the embedded static assets and forwards WebSocket binary bytes to one operator-configured SSH destination. It has no key enrollment API, holds no SSH private key, never terminates SSH and has no code path to a workspace socket. Before forwarding the server's first SSH reply it checks that the host key matches the configured `ssh_host_key`; browser OpenSSH verifies the same key and its signature independently.
- `kelpmux web-bridge --workspace NAME`: run by OpenSSH as the authenticated Linux user, without a PTY. It connects to that workspace's existing private socket, checks that the peer is a process of the same user and stays bound to that process, then relays the independent pane stream plus a small set of request-correlated operations. It never listens on TCP and never stops, restarts or replaces a workspace server. If its workspace's server is not running (no socket, or a socket nothing listens on), it tells the browser, which shows a **Start workspace** button; only that explicit click sends `start`, which runs the same code path as `kelpmux start --workspace NAME` for the bridge's own configured workspace and nothing else (no workspace name, server binary or replacement comes from the browser), and is refused while a server is running. The bridge then connects as usual. KelpServer removes agent and multiplexer session markers from the environment of the server it starts and of every pane shell (see [native.md](native.md)).

The `Web` operations the bridge accepts (API version 3, minor 9) are `state`, `new` (a shell in a new pane, optionally in a given absolute directory), `close` (explicitly confirmed), `search`, `history`, `status` (system status and processes), `closed` (the server's closed-session records the TUI's Recovery lists: recently closed terminals and previous runs, with their restore choices) and `restore` (explicitly confirmed: resume an agent conversation, rerun a command or open a shell in the original folder, in a new pane through the server's `restore`), `repos` (see below), `commands` (each live pane's foreground program, keyed by pane id: the base name of the first argument of its terminal's foreground process-group leader, or `null` when the pane's own process is in front, such as a shell at its prompt; process identities come from the server, never the browser, and arguments are never returned because they can hold secrets; at most 128 panes), `start` (only while the workspace server is stopped; see above), `config` and `config_set` (the user configuration file, below), the `projects` operations, `git` (see [Repos](#repos)), `conversations` (see [History](#history)) the environment operations (see [Environments](#environments)) and the `github_*` operations (see [GitHub](#github)). Each operation that reaches the server uses KelpServer's stream session API on a short-lived connection of its own, checked to reach the same server process and epoch as the relayed stream: `new` is `spawn` (idempotent per browser request identity), `close` takes the pane's lease and sends `close`, `search` and `history` are the stream requests of the same names, `closed` is `closed_sessions`, `restore` is `restore` for a record of the server's latest list, and `commands` reads the pane list of the first update. While stopped, the bridge answers the stream `hello` with a `{"Workspace":{"running":false,"workspace":NAME}}` notice and accepts only `state`, `start`, `config` and `config_set`. Stream requests, notification acknowledgements included, are forwarded unchanged; read marks are shared with the TUI. Every other method is refused with `unsupported web operation`. A web build refuses a bridge of another API version (and the reverse) with a message asking for matching versions; both ship in the same `kelpmux` binary. Version 3 removed `color`: tab colours are each client's own state ([ADR 0002](https://github.com/joanfabregat/kelpcore/blob/main/crates/server/docs/adr/0002-generic-session-server.md), decision 144b), and the web client has since dropped tab colours altogether (decision 177). Operations added within a version are additive: `state` reports `api_minor` (9 in version 3) and its `operations` list, and the web client uses an optional operation (`repos`, `commands`, `uploads`, `files`, `downloads`, `config`, `projects`, `git`, `conversations`, `environments`, `github`) only when that list names it, so an older bridge of the same version still serves a newer web build with those columns left plain, uploads off, no Files entry and no Download actions. Minor 1 added `uploads`, which is not a `Web` method: it says the bridge relays KelpServer's upload stream requests (`upload_begin`, `upload_chunk`, `upload_finish`, `upload_cancel`) and their events like any other stream request, unchanged, on the relayed connection (a bridge of minor 0 cannot parse them and would end the session). See [Uploads](#uploads). Minor 2 added `files`, which is not a `Web` method either: it says the bridge relays KelpServer's file stream requests (`file_list`, `file_stat`, `file_read`, `file_write`, `file_mkdir`, `file_rename`, `file_trash`, `file_delete`) and their replies (`file_list`, `file_stat`, `file_content`, `file_written`, `done`, `file_removed`, `file_error`) unchanged, with the Welcome's `file_limits`, on the relayed connection (a bridge of minor 0 or 1 cannot parse them and would end the session). See [Files](#files). Minor 3 added `downloads`, again not a `Web` method: it says the bridge relays KelpServer's download stream requests (`file_download_begin`, `file_download_ack`, `file_download_cancel`) and events (`file_download_started`, `file_download_chunk`, `file_download_done`, `file_error` with a `download`), and the Welcome's `file_limits.downloads`, unchanged (a bridge of minor 2 or older cannot parse them and would end the session). See [Files](#files) (Downloads). Minor 4 added `config`: `config` returns the user configuration (`~/.config/kelpmux/config.toml`; see [config.md](config.md)) as the bridge last validated it: `path`, `exists`, `revision` (a hash of the file), `current` (false while the file is invalid), `values` (as written) and `resolved` (with `~` expanded) of the configuration in effect (the last valid one while the file is invalid, else the defaults), and `errors` (`key`, `line`, `column`, `message`); `config_set` takes `{"changes": {"files.root": "~", "files.extra_roots": […], "projects.base": …, "scratch.folder": …}}`, validates the edited file with the same validator as `kelpmux config check` and saves it (locked, atomic, comments kept) only when valid, and returns `{saved, errors, config}`. The bridge watches the file and sends `{"Config": …}` (the same object as `config`) when it changes; the shared connection's worker forwards only stream events to its windows, so each window also asks `config` every five seconds. Minor 5 added `projects`: the operations `projects`, `project_move`, `project_create`, `project_update` and `project_delete`, the `project` parameter of `new`, the `project` of `closed` entries and the `projects` of the `config` object (see [Projects](#projects)); `new` without a project now starts in the Scratch folder. Minor 6 added `git`, the read-only Git facts of a project's checkouts (see [Repos](#repos)). Minor 7 added `conversations`, the History listing answered by the bridge's History thread, and the `resume` parameter of `new` (see [History](#history)). Minor 8 added `environments`: the operations `environments`, `environment_start`, `environment_stop`, `environment_check` and `environment_panes` (see [Environments](#environments)). Minor 9 added `github`: `github_status`, `github_test`, `github_repositories`, `github_clone`, `github_clone_cancel` and `github_state`, and the `github` (`owner/name`) of each `git` checkout (see [GitHub](#github)).

**Binary screens.** When the server's Welcome lists `binary-screens`, the browser's `Session` (in `@kelpcore/web`) sends the `binary_screens` stream request, which the bridge forwards like any other, and from then on the server follows each `update` with one binary screen record ([KelpCore binary-screens.md](https://github.com/joanfabregat/kelpcore/blob/main/crates/server/docs/binary-screens.md)). The bridge reads the server's records raw: JSON records are decoded and re-serialized as before, binary records (payload starting with `0x00`) are written to the browser byte for byte without parsing, in order, through the same bounded queue, and only after the Welcome has been relayed. The browser's WASM core decodes them into the ordinary JSON updates the rest of the client uses. A 300 × 80 snapshot is then about 16 KB instead of about 2.4 MB of JSON. The web assets rely on this bridge behaviour and need no extra negotiation, because the relay serves the assets embedded in the same `kelpmux` executable that runs as the bridge; an older bridge re-serializes every record as JSON and would end the session at the first binary record. The TUI opts in the same way and decodes the records natively (`tui::attach::Records`); the one-shot session API connections (`kelpmux ctl`, the bridge's own `Web` operations) never opt in and stay JSON.

`repos {"paths": [...]}` takes pane working directories (which the browser already has) and returns `{"repos": [...]}` in the same order, each entry `{"root", "branch", "detached", "github"}` or `null`. `root` is the directory holding `.git`; `branch` is the checked-out branch (`refs/heads/` removed); `detached` is the first twelve hex digits of a detached HEAD; `github` is `owner/repo` when the preferred remote (`origin`, else the first remote in the config) is on GitHub in its `https://`, `ssh://` or `git@github.com:` form. Credentials in a remote URL and non-GitHub remote URLs are never returned; such a repository shows its root without a link. The bridge computes this itself; KelpServer is not involved. It only reads files and never runs `git` or any other process: `.git` (a directory, or a file whose `gitdir:` names a linked worktree's or submodule's Git directory), `HEAD`, a worktree's `commondir` and the shared `config`. It is bounded and conservative: at most 64 paths per call (more is an error), only absolute paths without `.` or `..` components that are directories owned by the bridge's user, at most 32 directories walked up from each, Git metadata owned by another user or reached through a symlinked `.git`, `HEAD` or `config` is ignored, files are opened without following symlinks and without blocking (a FIFO cannot stall the bridge), `HEAD`, `.git` and `commondir` above 4 KiB and a config above 64 KiB are not parsed (the repository is still reported, without a remote), and config `include`s and `insteadOf` rewrites are not followed. Results are cached for one call only.

## Security boundaries

- Authentication is SSH public-key authentication by the host's OpenSSH server. There is no web password, cookie or session token. Each new SSH connection authenticates again.
- A key authorized for a Linux account grants that account's terminals, which run commands with that user's authority. Operators who want the key limited to the web bridge can authorize it with `restrict,verify-required,command="/path/to/kelpmux web-bridge --workspace NAME"`; this prevents unrelated SSH commands and forwarding, but a shell in a pane is still a shell.
- Run the relay under a separate restricted service identity (or an equivalent container) with no access to user home directories, credentials, workspace sockets or other processes. Putting the relay and the bridge in one executable is packaging, not isolation.
- The origin that serves the JavaScript and WebAssembly is trusted: a compromised frontend can read terminal contents and input even though the relay only sees SSH ciphertext. Serve it over HTTPS only, from a trusted build.
- The relay sets cross-origin isolation headers (required by WASSH), a restrictive Content-Security-Policy, `nosniff` and `no-referrer`, checks the `Origin` of WebSocket upgrades, and bounds headers, frames, buffers, connections and time.
- Browser storage holds only public data: credential handles, public keys, SSH fingerprints, key names/icons/colours, appearance, this browser's layout and its default upload folder. No private key, SSH transport state or token is stored, exported or shared with other pages.
- The upstream OpenSSH WASM build (`0.82`, OpenSSH 10.6 with OpenSSL 1.1.1w) and the WASSH JavaScript are fetched at pinned, checksum-verified revisions. RustSec and npm audits do not cover the compiled libraries inside that archive; treat the legacy OpenSSL copy as needing its own review before exposing the client beyond a private network.

## Build

The relay serves assets embedded at compile time from `web/dist`. A checkout without `web/dist` builds and runs the TUI and server normally; `kelpmux web-relay` then refuses to start with an explicit "no web client assets" error.

Prerequisites: Rust with the `wasm32-unknown-unknown` target and Node 24. Keep dependency fetching and auditing separate from building, and run builds in your usual isolated environment:

```sh
# 1. Portable terminal core for the browser (kelpclient, from the pinned KelpCore revision).
cargo build --locked -p kelpclient --release --target wasm32-unknown-unknown
cp target/wasm32-unknown-unknown/release/kelpclient.wasm web/public/client-core.wasm

# 2. Pinned WASSH and OpenSSH WASM (download and verify only; executes nothing).
bash scripts/fetch-web-ssh.sh

# 3. Locked JavaScript dependencies (with @kelpcore/web from GitHub at the pinned
#    KelpCore commit), without install scripts, then audit.
(cd web && npm ci --ignore-scripts && npm audit --audit-level=high)

# 4. Test, type-check, lint the React hook rules (oxlint) and build the static client.
(cd web && npm test && npm run check && npm run lint && npm run build)

# 5. Build kelpmux, which embeds web/dist.
cargo build --locked --release --bin kelpmux
```

Build the web assets before compiling the executable that embeds them; rebuild `kelpmux` after every web change. `node_modules`, `web/dist`, `web/sourcemaps`, `web/public/vendor` and `web/public/client-core.wasm` are generated and ignored by Git. `npm run build` also writes the client's source maps to `web/sourcemaps/` (never to `web/dist`, so they are neither embedded nor served) and its release name to `web/sourcemaps/RELEASE`; see [Error reporting](#error-reporting).

`npm test` runs the application's unit tests (`test/*.test.mjs`) with `node --import ./test/ts-loader.mjs`: Node strips TypeScript types itself but refuses to under `node_modules`, so that small load hook strips them from `@kelpcore/web` with Node's own `module.stripTypeScriptTypes` (no extra dependency). ## Relay configuration

Start the workspace with the ordinary launcher (`kelpmux start --workspace main`), make sure OpenSSH accepts key logins for the account, then run the relay with a JSON configuration (see [examples/web-relay.json](../examples/web-relay.json)):

```json
{
  "enabled": true,
  "listen": "127.0.0.1:8080",
  "origin": "https://terminal.example.com",
  "ssh_target": "127.0.0.1:22",
  "ssh_host_key": "ssh-ed25519 AAAA…",
  "username": "alice",
  "bridge_command": "/opt/kelpmux/current/kelpmux web-bridge --workspace main",
  "workspace": "main",
  "dev": false,
  "glitchtip_dsn": null,
  "error_environment": null,
  "idle_warning_minutes": null,
  "idle_lock_minutes": null
}
```

```sh
kelpmux web-relay --config /etc/kelpmux/web.json
```

- `enabled` must be `true`; the relay refuses to start otherwise.
- `listen` is the local address; put a TLS-terminating reverse proxy with WebSocket support in front of it.
- `origin` is the exact HTTPS origin users open. Its host name is also the WebAuthn relying-party ID, so keys registered for one origin do not work on another.
- `ssh_target` is the one SSH destination the relay may reach. `ssh_host_key` is that server's Ed25519 public key (algorithm and base64, from `/etc/ssh/ssh_host_ed25519_key.pub` obtained through a trusted path), not a fingerprint and never a private key.
- `username` is the Linux account; `bridge_command` is the exact command the browser asks OpenSSH to run (use absolute paths: a noninteractive SSH session may have a minimal `PATH`, and shell startup files must not print to standard output). `workspace` names the workspace for display.
- `dev` only adds a DEV badge to the interface.
- `glitchtip_dsn` (optional, default unset) turns on [error reporting](#error-reporting) to a GlitchTip project; `error_environment` (optional, default unset) names the environment events are filed under, such as `preprod`. Without a DSN nothing is reported and the browser loads no reporting code.
- `idle_warning_minutes` (optional, integer 1–1440, default 60) and `idle_lock_minutes` (optional, integer 1–240, default 15) set the [idle lock](#idle-lock): after `idle_warning_minutes` without activity every KelpMux window of a browser shows a warning with a countdown, and if nothing happens within `idle_lock_minutes` more the shared connection locks. Any other value stops the relay at startup. Each one set is handed to the browser in `/connection.json` under the same name; unset (or `null`), the browser uses the default.

Hosting is the operator's responsibility; nothing installs a service. Start with private or VPN-only access.

## Error reporting

Optional and off by default: KelpMux can report errors to a [GlitchTip](https://glitchtip.com) project (self-hosted and Sentry-compatible) with the Sentry SDK. It reports errors and crashes only. There is no performance tracing, session replay, profiling, session tracking or cron monitoring (GlitchTip has none of the last three anyway).

**Components.** The web client reports with the Sentry browser SDK (component `web`). The `kelpmux` executable reports with the official `sentry` Rust crate (see [native.md](native.md#error-reporting)): the relay's own panics and SSH-leg errors (`relay`, from the same `glitchtip_dsn` and `error_environment`), `web-bridge` panics (`bridge`) and TUI panics (`tui`), the last two from `KELPMUX_GLITCHTIP_DSN` and `KELPMUX_ERROR_ENVIRONMENT` in their environment. The relay reports two errors it also logs to stderr, each at most once a minute: `relay.ssh_connect` (the SSH target refused or timed out) and `relay.ssh_handshake` (the target's SSH handshake failed the pinned host-key check), with the OS error or the relay's fixed message as text. It does not report per-request errors such as a wrong origin or a malformed request.

**Configuration.** Set `glitchtip_dsn` in the relay's configuration to the project's public DSN, `https://KEY@HOST[:PORT]/PROJECT_ID`, and optionally `error_environment` (1–64 letters, digits, `.`, `_` or `-`). The relay checks both at startup and refuses an `http://` DSN or one with a secret key, since the DSN is handed to every browser. When a DSN is set, `/connection.json`, the bootstrap document the browser already reads from the relay, gains `"errors": {"dsn": …, "environment": …}`, and the relay adds the DSN's origin (`https://HOST[:PORT]`) to the `connect-src` of its Content-Security-Policy. Without a DSN neither changes, the browser never loads the reporting code (a separate chunk, `assets/error-reporting-*.js`, about 64 kB, 22 kB gzipped) and nothing is sent. Reports are cross-origin `fetch` requests in CORS mode, which cross-origin isolation (COOP/COEP) allows; GlitchTip answers them with the needed CORS headers.

**What is sent.** Uncaught errors and unhandled promise rejections, with their `cause` chain and duplicates dropped, through a bare `BrowserClient` with only those integrations. That means no breadcrumbs (console, DOM, fetch, navigation), no user, IP inference (`infer_ip: never`), cookies, headers, request bodies or query parameters, no client reports, and none of the SDK's default integrations. A `beforeSend` hook additionally removes `user`, `breadcrumbs` and `extra`, reduces `request` to its URL, and strips query strings and fragments from that URL and from every stack frame's file name. Events are tagged `component: web` and carry the build's release and the configured environment. KelpMux never adds terminal content (text, input, titles, folders or commands) as tags, extra data or context. An error message is sent as thrown, so error messages must not include terminal content either.

**Pages and workers.** Every page of the client, popped-out terminals included, starts reporting the same way after reading `/connection.json`. The SharedWorker that holds the SSH connection does not load the SDK: keeping it out of the page that holds SSH transport state is simpler and safer, and the worker's failures already reach the pages that use it, which show them.

**Release name.** `kelpmux@VERSION+SHA`: the version from `Cargo.toml` and the first 12 hex digits of the Git commit, for example `kelpmux@0.2.0-beta.7+c5b489c1a2b3`. Without Git information it is `kelpmux@VERSION`. `KELPMUX_GIT_SHA` supplies the commit when the build has no Git checkout, and `KELPMUX_RELEASE` overrides the whole name (letters, digits, `.`, `_`, `@`, `+`, `-`; at most 200). The web build (`web/scripts/release.mjs`, through Vite's `define`) and the Rust build (`build.rs`, as `kelpmux::native::error_reporting::RELEASE`) compute it the same way, so one build reports one release. When the web build ran without Git (in a container without the repository's `.git`, for example) and the Rust build with it, the two would differ: `build.rs` warns when `web/sourcemaps/RELEASE` names another release. A deploy should set `KELPMUX_RELEASE` (or `KELPMUX_GIT_SHA`) for both builds.

**Source maps.** For each build, the deploy uploads the client's source maps to the GlitchTip project for the release in `web/sourcemaps/RELEASE`, before or when it ships that build. Vite builds them as hidden maps (no `sourceMappingURL` comment) and moves them out of `web/dist`, so the relay neither embeds nor serves them. The browser loads scripts from `/assets/`, so stack frames reference `https://ORIGIN/assets/NAME.js`. Upload, under the URL prefix `~/assets/`:

- each minified script `web/dist/assets/NAME.js` as `~/assets/NAME.js`: `index-*.js` (the application), `error-reporting-*.js` and `session-worker-*.js`;
- its map `web/sourcemaps/assets/NAME.js.map` as `~/assets/NAME.js.map`.

Because the scripts carry no `sourceMappingURL`, the uploader must link each script to its map: `sentry-cli` does so for `NAME.js` and `NAME.js.map` in the same directory. For example, stage both into one directory, then run `sentry-cli --url https://GLITCHTIP sourcemaps upload --release "$(cat web/sourcemaps/RELEASE)" --url-prefix '~/assets' STAGING_DIR`. With another uploader, give each script the artifact header `Sourcemap: NAME.js.map`. Never copy the maps into `web/dist`: `build.rs` skips `*.map` files, but anything else there would be served publicly.

## Registering a YubiKey

1. Open the HTTPS origin. On the sign-in page choose **Register a new key**, then **Register new key**, and touch the key. This creates a discoverable ECDSA P-256 credential with required user verification, scoped to this origin. It grants nothing on its own.
2. Copy the displayed OpenSSH public key (`sk-ecdsa-sha2-nistp256@openssh.com …`) and add it to the account's SSH authorization through your usual mechanism (for example `~/.ssh/authorized_keys`, optionally prefixed with `restrict,verify-required,command="…"` as described above). The web client never edits SSH authorization.
3. Choose **Sign in with security key** and touch the key. When this browser remembers the last key used, one touch signs the login. **Use another security key** (or a new browser) first asks the authenticator which credential to use; because WebAuthn assertions do not return the public key, the browser recovers the candidate public keys from that signature and offers them all to OpenSSH, which asks the server which one is authorized before requesting a second touch to sign. Nothing needs importing on a new browser.
4. If the server accepts none of the candidates, the page says the key is not authorized for the account.

Register and authorize each physical key separately. Settings → Security keys names keys, picks the one used for the next sign-in, shows public keys and exports or imports public registrations; these details stay in this browser. Removing a key there does not delete the credential from the authenticator or revoke its SSH authorization. Removing the SSH authorization stops new logins; it does not end existing SSH sessions.

## Using it alongside the TUI

The TUI and the web client are independent clients of the same KelpServer. You can use the TUI alone, the web alone, or both at once on the same panes and processes:

- Layout is per client. The TUI keeps its grid, tabs, parking, tab colours and focus; each browser keeps its own view mode, terminal order, parked terminals, focused terminal, sidebar width and folding in `localStorage` (layout per workspace, discarded when the server restarts with a new epoch). Neither changes the other's layout. The web client has no tab colours (decision 177); the TUI's colours stay in the TUI, and a layout stored by an older web build with colours still loads, its colours ignored. Parking in the browser hides a terminal from this browser's list and grid only; it keeps running and stays visible in the TUI. Parking in the TUI likewise stays in the TUI: parking is each client's own state, and KelpServer 0.3 reports every pane as unparked.
- Notification read marks are shared. Showing a terminal in the browser marks its notifications read for every client, as the TUI does when it shows one: the terminal shown on its own (or in its popup window). The live grid is read-only and marks nothing read: its tiles keep their bells until their terminal is shown. A notification that arrives for the shown terminal is marked read at once while the browser window is visible and focused; one that arrives while the window is hidden or in the background keeps the bell until the window is looked at again, and a hidden window never marks anything read. The bell in a terminal's header opens its notifications, mainly as a history (**History** by default, with **Unread**, **Mark read** and **Mark all read** too). The TUI's marks show in the browser and the browser's in the TUI. The browser's alerts (in-app toasts, the favicon bell and the optional sound; see [Notifications](#notifications)) are this browser's own preferences (Settings → Notifications).
- Creating or closing a terminal is shared: a new pane appears in every client, and closing one (always confirmed) ends its processes for everyone.
- Input and size follow whichever client last used a pane. When a browser focuses a terminal or types into it, it claims that pane's input and size lease and resizes the PTY to its own view. When the TUI's controlling client then types, pastes, clicks or focuses that pane, the TUI takes it back and the pane returns to the TUI's geometry. The live grid is a foreground layout too: while the browser window is focused and visible, it sizes each tile's pane to that tile (claiming it), so opening the grid in a browser resizes the panes it shows until the TUI uses them again. A tile claims the lease only to size its pane: the grid has no focused tile and sends no keyboard, mouse, paste or touch input, and no keyboard action addresses a tile. Passive rendering in a background window, mouse movement, window blur and focus-out never take a pane. Each pane has exactly one PTY size; a client that does not hold the lease shows the pane clipped or padded. Different panes can be held by different clients at the same time.
- The focused terminal's header shows a **TUI** or **Other browser** badge while this browser does not hold its input and size (hover it for details). Closing the browser or losing the connection releases its leases; terminals keep running and return to the TUI's geometry.
- Only one TUI client is the controller (input and workspace size); further TUI clients are observers, as before. Web clients are not TUI controllers or observers and do not affect that role.

Other same-origin tabs and **Open in a window** popups reuse the SSH connection held by the first tab through a SharedWorker; keep that tab open. **Log out all browser windows** (Settings → Connection) or `Ctrl-B d` closes SSH for every window of the browser; workspace processes keep running.

## Notifications

The browser alerts with in-app toasts in the top right corner of the app, at the top of the one toast stack (download progress and confirmations such as "Path copied" follow below them, newest first, so the toasts never overlap; on a phone the whole stack is full width under the terminal bar); it no longer uses the browser's desktop notifications (Web Notifications API) or asks for their permission (owner decision, 2026-11-22). A toast appears for each new workspace notification of an enabled event: **Question** (input needed), **Finished** (a turn finished), **Failed**, **Exited** (an agent exited) and **Bell** (an agent rang the terminal bell), the TUI's event names (`notification_events`). KelpServer records these events for agents only. Notifications already there when the browser connects make no toast.

- **One toast per terminal.** A new event of a terminal that already has a toast updates that toast (its newest event, raised to the top) instead of adding one. A bell that accompanies a typed event (same terminal and process, within two seconds) shows as that event, so a question with its bell makes one toast; KelpCore will later merge the two on the server.
- **More than three toasts collapse** into one summary ("5 terminals need attention"); a click expands it into the list of terminals.
- **Clicking a toast** or a summary entry opens its terminal exactly as choosing it in the sidebar does: shown alone (leaving the grid, unparked if parked), or opened full screen on a phone. Showing it marks its notifications read, which removes the toast.
- **No toast for the terminal being read**: the terminal shown alone, while the window is visible. The read-only grid has no focused terminal and marks nothing read, so every grid tile gets toasts, as it keeps its bell. Popup windows show no toasts; their main window does.
- **Toasts go when read anywhere**: when the terminal's notifications are marked read in this window, another browser window or device, or the TUI (read marks are KelpServer's workspace state, shared by every client), when the terminal or its process ends, or when the event is turned off. They have no timer. The close button only hides a toast; the terminal's notifications stay unread and its bell stays in the sidebar.
- **Favicon bell.** While an unread bell remains, the browser tab's icon gets an amber dot in its top right corner, removed when the bell is read. It follows the Bell event setting.
- **Phones.** Toasts span the width minus the 16 px gutters, below the safe area and the terminal bar, away from the key bar at the bottom.

Settings → Notifications has one toggle per event, all on by default like the TUI's, and the sound (off by default), which plays for the same enabled events. These preferences are stored per browser (`notificationEvents` in `kelpmux-web-preferences`); the former **Desktop** choice stored by earlier builds is ignored and dropped on the next save.

## Idle lock

The shared connection locks when nobody uses it (decisions 163–165). After 60 minutes without activity in any KelpMux window or popup of the browser, every window shows a warning with a live countdown ("KelpMux locks this connection in 14:59. Your shells keep running.") and a **Stay signed in** button. Any activity in any window, the button included, lifts the warning in every window; if nothing happens within 15 more minutes, the connection locks for every window, which then shows the sign-in page with the reason. Shells and jobs keep running; signing in with the security key reconnects. Both durations can be changed in the [relay configuration](#relay-configuration) (`idle_warning_minutes`, `idle_lock_minutes`).

- **Activity** is a key press, a click or tap, a touch or scrolling anywhere in a KelpMux window, and terminal input, paste, mouse reporting, uploads and deliberate actions as before. Terminal output, mere pointer movement, background polls and window heartbeats do not count. Each window reports its activity to the shared worker at most once every 30 seconds (at once while the warning is shown).
- **Wall-clock deadlines.** The shared worker checks the deadlines with timers, every 10 seconds and before handling any message from a window, against the clock rather than elapsed timer time. A browser that throttled or suspended the worker (background tabs, a sleeping laptop, a phone with the screen off) locks as soon as it wakes if both durations have passed, without showing the warning first; the first key press after waking cannot revive the connection.
- Without SharedWorker support (each window then holds its own SSH connection) there is no idle lock.

## Uploads

Files and images dropped onto a terminal are uploaded to the host where its shells run, and their paths are pasted into that terminal, through KelpServer's `uploads` stream capability (decision 151a; see the [KelpServer protocol](https://github.com/joanfabregat/kelpcore/blob/main/crates/server/docs/native-client-protocol.md#uploads-uploads)). The [file browser](#files) can also upload files dropped onto a folder into that folder.

- **Drop targets.** Drop one or more files or images onto the terminal shown on its own (the read-only live grid takes no drops). Pasting an image (a clipboard with files and no text, such as a screenshot) into a terminal does the same. Every terminal's menu (right-click, or **⋯** on phones and tablets) also has **Upload files…**, which opens the system file picker, so iPhones and iPads, which have no drag and drop onto a page, can upload too. Files dropped elsewhere on the page are ignored rather than opened by the browser.
- **Dialog.** Nothing is sent until the upload dialog is confirmed. It shows the target terminal, each file's name and size, the total and the destination folder. Folders cannot be uploaded: a dropped folder is listed as skipped. The server's advertised Welcome `upload_limits` are enforced before anything is sent (64 files, 100 MiB per file and 1 GiB per drop by default); a drop over a limit explains which one and cannot be started.
- **Destination.** By default each drop gets its own new private folder in the server's upload folder (`~/.cache/kelpserver/uploads` unless the server is configured otherwise with `kelpmux start --upload-dir`; KelpServer deletes completed uploads there after its retention, 7 days by default, set with `--upload-retention-days`; see [native.md](native.md#named-workspaces)). Settings → **Uploads** sets a default destination folder instead: an absolute path on the server host, which must be an existing folder owned by the account (KelpServer checks this), sent as `dest`; each drop then gets its own private folder inside it. The setting is kept in this browser only. The dialog can change the folder for one drop, with **Remember as the default destination in this browser**.
- **Progress and cancel.** The dialog shows each file's progress and the total. The client sends chunks of at most 128 KiB (or the server's smaller `max_chunk_bytes`) and never has more than the server's `max_chunks_in_flight` unacknowledged on the connection; windows sharing one SSH connection share that window through the SharedWorker, which also routes each upload's events to the window that began it and cancels the unfinished uploads of a window that closes. **Cancel upload** sends `upload_cancel`, and the server removes the batch with its partial files. A refusal (a missing or foreign destination, too many uploads at once, not enough space) or a failure is shown in the dialog, and nothing is pasted.
- **Paste.** When the upload is done, the absolute paths are quoted for POSIX shells (`'…'`, with `'` written as `'\''`, unless a path only has safe characters) and pasted, space-separated, into the terminal the files were dropped on, as a paste: bracketed when the program has bracketed paste on, and without Enter, so nothing runs until you press it. Pasting takes the terminal's input and size, as typing does. If that terminal closed during the upload, the dialog lists the paths with copy buttons instead.
- **Requirements.** The server must offer the `uploads` capability and the bridge must report `uploads` in its operations (API 3, minor 1); otherwise a drop opens the dialog with the reason (restart the workspace with a current KelpServer, or install matching KelpMux versions) and sends nothing.

Uploading is the same trust as typing into a shell: anyone signed in can already write any file the account can write. The paths come from the server and are checked by the WASM core (absolute, no control characters) before they can be pasted.

## Files

The **Files** entry at the bottom of the sidebar opens a file browser of the server user's files, rooted at the file root (the home folder by default, see below), in the main area; files open from it in a text editor in the same place (see [Layout](#layout)). The sidebar has no file tree. Both use KelpServer's `files` stream capability ([KelpServer protocol](https://github.com/joanfabregat/kelpcore/blob/main/crates/server/docs/native-client-protocol.md)) on the existing SSH connection; the bridge relays the requests and replies unchanged (API 3, minor 2). The browser and editor components, the request client and the CodeMirror editor are KelpCore's `@kelpcore/web/files/` (derived from KelpHub's); KelpMux supplies the views, the sidebar entry and the wiring.

- **The file root.** KelpServer confines every file operation to one folder, the server user's home folder unless it was started with `--files-root` (or `files_root` in `workspace.json`), and advertises it as Welcome `file_limits.root` (KelpCore 3a7d99c). The browser starts there, the breadcrumbs begin with it (**Home** when it is the home folder, else its path) and the parent folder button stops at it. Nothing outside it is offered: a folder or file asked for outside it (a `?view=files&dir=…` or `file=…` link, a terminal's folder, a side panel file) shows the root instead with a toast, replacing the history entry; an upload destination typed outside it is refused; path links outside it are not candidates (no `file_stat` is sent); drops and moves only target folders inside it. A symbolic link pointing outside it is listed with its link icon, dimmed, and its target in the tooltip, but does not open or download; its menu keeps the actions on the link itself (insert or copy its path, rename, trash, delete). The root itself is never downloaded, renamed, moved, trashed or deleted. The check is lexical (`web/src/files/root.ts`, unit tested); KelpServer enforces the root itself and refuses anything outside it with `outside_root`, which the views show as "Outside the folders this server lets you browse". A server without `file_limits.root` (before KelpCore 3a7d99c) keeps the earlier behaviour, rooted at `~` with `/` reachable. The bridge relays the field and the error code unchanged; its API version is unaffected. The root comes from `files.root` (and `files.extra_roots`) in the user configuration, `~/.config/kelpmux/config.toml`, which `kelpmux start` records in `workspace.json` when it launches the server; Settings → **Files & folders** edits it, and a changed root applies on the next workspace start (see [docs/config.md](config.md)).
- **Browsing.** A column view like the Finder's (`web/src/files/FilesBrowser.tsx`): the first column is the file root; selecting a folder opens its listing in a new column to its right, replacing any deeper columns, and selecting a file (or a link to one, or a special file) shows an info column at the far right with its icon, name, kind, size, modification date and folder, where a link points, the first 40 lines of a text file up to 32 KB (one `file_read` per selection), and **Open**, **Open beside terminal** and **Download**. A double-click or Enter opens a file in its tab; a symbolic link opens what it points to (a folder as the next column). Each column lists folders first, then files, by name in natural order, each row with the entry's icon and name and, under the name, smaller and muted, its modification date (**Today 14:32**, **Yesterday 09:10**, else the date in the browser's locale) and size in decimal units like the Finder (**4.2 KB**; folders say **Folder**, links where they point); folders carry the Finder's chevron. The formatting is `web/src/files/columns.ts`, unit tested. The highlighted entry is grey in the other columns and tinted in the column the keyboard is in. Columns are 260 pixels wide; dragging a column's right edge resizes it (160 to 640 pixels, a double-click restores it, not kept across reloads), each column scrolls on its own, and the column area scrolls sideways, keeping the newest column in view. The keyboard works as in the Finder: ↑ and ↓ move within a column (a folder shows its column as it is reached), → enters the selected folder's column at its first entry, ← returns to the parent column, Enter opens, typing selects the first name starting with what was typed, and the context menu key or Shift+F10 opens the entry's menu; the focused row has a focus ring. Hidden entries (names starting with `.`) show only after the eye button, a choice kept in this browser. The breadcrumbs above the columns show the deepest folder shown (Home for the home folder) and a click truncates the columns to that folder; the parent folder button, **Refresh** (every column), **New file**, **New folder** and **Upload** (into the folder of the column the keyboard is in, named in their tooltips) sit beside them. A truncated listing says so at the end of its column. Phones have no room for columns: they show the deepest folder alone at full width, with the same two-line rows, the breadcrumbs (scrolled to the deepest folder) and the parent folder button to go back up, and no info column; a tap opens a folder or a file. Each terminal's header has a folder button (and its menu **Browse files here**) that opens the browser at that terminal's current folder.
- **Operations.** Each row's **⋯** button (or a right-click) has **Open**, **Insert path into terminal N** (the terminal last shown alone), **Copy path**, **Download** (a folder: **Download as .tar.gz**; see below), **Rename…** (inline), **Move to trash** (the freedesktop trash, `$XDG_DATA_HOME/Trash`, as file managers use; a file on another file system than the trash must be deleted instead) and **Delete permanently…**, which asks first. Dragging an entry onto a folder row (in any column) or breadcrumb moves it there. Open editors and the columns follow renames and moves (a folder shown as a column keeps its column under its new name, a removed one gives way to its parent); trashing or deleting closes the unchanged editors inside and leaves changed ones open with a note.
- **Paths into terminals.** Dragging an entry onto a terminal's sidebar row, or onto the terminal shown, types its path into that terminal, quoted for POSIX shells as uploads paste theirs, as a paste and without Enter. A path with control characters is refused rather than typed.
- **Uploads into a folder.** Files dropped from the desktop onto a folder row, a breadcrumb or a column (its empty area or a file row in it) upload into that folder (the **Upload** button opens the file picker for the folder of the column the keyboard is in), with progress and Cancel above the columns. KelpServer puts each upload in a private batch folder inside the destination; the browser then moves each file out of it into the folder and removes the empty batch folder. A name already taken in the folder keeps its file in the batch folder, and the message names it. Files dropped onto a terminal still upload as described in [Uploads](#uploads).
- **Downloads.** **Download** in a file's menu, or the download button in the editor's header, saves the file to this computer; **Download as .tar.gz** in a folder's menu saves the folder and everything in it as one gzip-compressed tar archive named after it. KelpServer streams the bytes in chunks the browser acknowledges once written (`file-downloads`, KelpCore's `saveDownload`), so a download never fills the connection or holds back terminal output. Where the browser has the File System Access API (Chromium), the save dialog comes first and the bytes go straight to the chosen file; elsewhere they are collected in memory, up to 1 GiB, and handed to the browser's downloads at the end. A progress toast in the top right toast stack (below the [attention toasts](#notifications), above the confirmations) shows each running download with **Cancel**, which stops it on the server and discards the partial file. Archives keep symbolic links as links, never follow them, stay on the folder's file system, keep permission bits and modification times (no owners), and leave out special files and unreadable entries (counted in the final notice); a folder over the server's entry or size bounds is refused before anything is sent. The editor downloads the saved file, not unsaved edits. Without the `file-downloads` capability, or with a bridge older than API 3.3, there are no Download actions.
- **Editor.** CodeMirror 6 with syntax highlighting chosen from the file name, search (`Ctrl/Cmd+F` inside the editor), line numbers and the app's theme colours; it is loaded only when the first file opens. Open files are tabs in a strip that is the Files view's topmost bar, as tall as a terminal's header so the views line up, with the browser's breadcrumbs or the shown file's header (name, folder and its buttons) directly under it: the first tab, **Files** with the folder icon, is the file browser at its folder and never closes; each file open in the main area follows it as a tab, in opening order, with its name (and, when another open file has the same name, the shortest run of parent folders that tells them apart, like VS Code), its full path as the tooltip, a dot while it has unsaved changes and **×** (also a middle-click) to close it. Clicking a tab shows its file; opening a file from the browser, a path link, search or a link adds its tab or shows the existing one. Closing the file shown shows the next tab (else the previous one, else the browser). The strip scrolls sideways (a vertical wheel scrolls it too) and keeps the shown tab in view; phones get the same strip, compact. The sidebar does not list open files. `Ctrl/Cmd+W` stays the browser's, and there is no tab shortcut (Alt+W types a character on macOS and is a readline key). Each open file keeps its editor, with any unsaved changes, while a terminal, the grid or another file shows; closing a changed file asks first, and the page warns before unloading while any file has unsaved changes. **Save** (`Ctrl/Cmd+S`) writes with the hash the file was read at: if the file changed on disk since, a dialog offers **Reload** (discarding the edits), **Overwrite** or **Cancel** (keep editing). Binary files and files larger than the server's `max_read_bytes` (8 MiB by default) show an information view instead. Text files larger than 2 MiB (the largest single write the browser sends through the bridge) or the server's `max_write_bytes` open read-only.
- **Side panel.** A file can also open in a panel docked to the right of the terminal shown alone: **Open beside terminal** in a file row's menu opens it beside the terminal last shown alone and switches the main area to that terminal, and the editor's **Move beside terminal** button moves a file shown in the main area there (the panel's own button, **Open in the main area**, moves it back). There is one side panel per window, showing one file with the editor's usual header (name, folder, dirty dot, Save, Reload, Show in folder, Close); the panel's file has no tab in the Files view (one buffer per path: a file is either in the panel or a tab), and opening it again from the browser shows the terminal with the panel; **Open in the main area** moves it to a tab, as does a Back or Forward to it in the main area when it has no unsaved changes. Opening another file in the panel replaces the one shown, which stays open as a tab (one with unsaved changes is closed after asking). It is the same editor and document as in the main area: `Ctrl/Cmd+S` saves while the focus is anywhere in the panel, conflicts offer the same Reload, Overwrite or Cancel, and the panel's Close closes the file (asking first when it has unsaved changes). A file moves between the main area and the panel only without unsaved changes (save first), because the buffer lives in the mounted editor. Dragging the panel's left edge resizes it; the width is kept in this browser like the sidebar's, and the terminal always keeps at least 240 pixels. The terminal re-fits its columns and rows when the panel opens, closes or is resized. Clicking the terminal gives it the keyboard; clicking the editor gives it to the editor. The panel hides while the grid, the file browser or an open file in the main area shows and reappears, with its unsaved edits, beside the terminal shown alone.
- **Path links.** With Cmd or Ctrl held, a file path printed in the terminal shown alone becomes a link: hovering it underlines it and shows a pointer, and clicking opens a file in the side panel at its line and column, or a folder in the file browser. Nothing is scanned in advance. At the cell under the pointer the client takes the token from that row's text: the text between quotes when the pointer is inside a quoted span (which may hold spaces), otherwise the run of non-space characters, without leading brackets or quotes and trailing punctuation (`.,:;)]}>` and quotes). It accepts `path`, `path:line` and `path:line:col`, `./rel`, `../rel`, `~/x`, absolute `/x` and bare relative names, resolved against the terminal's current folder; URLs (`scheme://…`) and tokens of only dots, slashes and tildes are not paths. Only something that exists is a link: a `file_stat` request, sent once the pointer rests for 80 ms and remembered for five seconds, decides it. An OSC 8 hyperlink keeps its own behaviour: an `http(s)` one opens on any click, Cmd/Ctrl included, and a `file://` one is used as the path. The click is taken before the terminal's own handling, so it neither starts a selection nor reaches an application that turned mouse reporting on; every other click, drag and wheel event, with or without the modifier, behaves as before. A path wrapped across two rows is not joined (the screen model carries no soft-wrap marks), terminal history scrolled back has no links, and neither do grid tiles or popup windows. The parsing is `web/src/files/path-links.ts`, pure functions with unit tests, which could move to `@kelpcore/web`.
- **Phones.** A phone has no side panel: **Open beside terminal** opens the editor full screen, as **Open** does, and the editor has no move button.
- **Requirements.** The Files entry shows only when the server's Welcome lists the `files` capability with `file_limits` and the bridge reports `files` in its operations. Without them there is no side panel, no **Open beside terminal** item and no path links.

Like uploads, the browser and editor are the same trust as a shell: anyone signed in can already read and write any file the account can, and the file root limits the browser, not the account. KelpServer resolves `~`, enforces the file root and its own limits (entries per listing, paths per request, requests in flight, read and write sizes) and refuses to remove `/`, the home folder or the root.

## Projects

A project is a name and a folder; it groups terminals in the sidebar and scopes the grid, the file browser and [History](#history). Projects are stored in the user configuration as `[[project]]` tables (see [config.md](config.md#projects-for-agents)), so the web client, an agent or a text editor can add one; KelpMux checks them with the rest of the file (unique ids and names, the folder inside the file roots, no project folder inside another's or containing it, none overlapping `scratch.folder`). **Scratch** is built in, on `scratch.folder`: it cannot be renamed or deleted, and it holds every terminal that belongs to no other project.

- **Membership.** A terminal belongs to exactly one project, decided when it is created and never inferred from its current folder: **New terminal** creates a terminal in Scratch, in the Scratch folder (created on first use); a project's **+** creates one in the project's folder. Dragging a row onto another project's group (its header or one of its rows), or the row menu's **Move to project…** (the keyboard's and touch devices' way), changes only the membership: the shell stays where it is. The bridge keeps the links in the workspace's state folder (`terminal-projects.json`, written under a lock and replaced atomically), keyed by the server run and pane (the same key as the server's closed-terminal records), so they survive a reload, show in every browser within five seconds, and carry over to History and to a restored terminal. A terminal whose project was deleted, or whose link was lost, is Scratch's.
- **Sidebar.** With at least one project besides Scratch, the terminals are grouped by project: the user's projects by name, then Scratch. Each group has a header with a chevron to fold it (remembered by this browser), then the project's colour, its name, its terminal count (folded: its agent state counts too), which open its [home page](#project-home-page), a quiet **+** and a menu: **Overview** (the home page; not offered on that page itself), **New terminal**, **Files**, **Repos** (with `git`), **Environments** (with `environments`; not for Scratch), **Terminals**, **History**, and for the user's projects **Rename…** and **Delete…**. A project whose folder disappeared shows a warning and cannot start terminals. Terminal numbers, the grid and `Alt+digit` follow the sidebar's order. Without projects the sidebar stays a flat list. **New project** sits under **New terminal**.
- **Dialogs.** **New project** asks for a name, a folder (empty: `<projects.base>/<name>`, created when missing) and an optional colour; **Rename** changes the name and colour (the id and folder stay). Problems show under their field, checked first in the browser and then by the bridge's validator, whose refusal leaves the file untouched. **Delete** removes the project from the configuration only: its folder and files stay, and its terminals become Scratch's. Ids are slugs of the name and are never reused while a link names them.
- **Project views.** A project's **Terminals** is the grid of its terminals, with a bar naming the project and **All terminals**. Its **Files** start the columns at its folder (the parent button stops there) with **All files** to leave. Its **History** lists its closed terminals and its conversations started outside KelpMux only (Scratch's: those of no existing project, and those in the Scratch folder) with **All projects**. The sidebar's **Grid** and **Files** show every terminal and every file.
- **File browser.** A project's folder shows in the project's colour in every column and in the breadcrumbs, with "Project NAME" in its details; a column inside a project has a thin rule in its colour, and the header links to the project's files. A folder's menu has **Create project from this folder…**, which is not offered on a project's folder and refuses a folder inside or containing another project's.

The bridge's operations are `projects` (pane id → project id for the running server's terminals), `project_move` (`{pane, project}`, `null` for Scratch), `project_create` (`{name, folder?, color?}`), `project_update` (`{id, name?, color?}`, a `null` colour removes it) and `project_delete` (`{id, confirmed: true}`); the last three edit `config.toml` like `config_set` and return `{saved, errors, config}`, with a create's `project` id. `new` takes an optional `project`, `closed` entries carry their `project`, and the `config` object lists `projects` (`id`, `name`, `folder` as written, `path`, `color`, `missing`).

## Project home page

A project's home page (its name in the sidebar, its menu's **Overview**, or `?view=project&project=<id>`) lists what the project holds on one page, a single centred column of cards (at most 960 pixels wide; full width on a phone). Scratch has the same page; with no project besides Scratch the sidebar is not grouped, so its page is reached by URL only. The title bar names the project.

- **Header.** The project's colour and name, its folder with a button copying its path (and a warning when it is missing), **New terminal** (in the project's folder), **Open in Files** (when the connection offers files), **Environments** (a link to the [Environments view](#environments), when the connection offers environments; not for Scratch; the page itself asks nothing about environments) and the project's menu.
- **Agents & terminals.** The project's live terminals, parked ones included and marked, agents first, then the others, each group in the sidebar's order: the state mark and its label (the Terminals table's words for agents: Working, Waiting on you, Finished, Failed, Idle; the state's for a plain terminal), the provider's logo, the title, the folder and how long since its last activity, with its unread bell. A click opens the terminal (unparking it). Empty: **New terminal**. **See all** opens the project's grid (a phone's terminal list).
- **Repos.** One line per checkout from the same `git` facts as the [Repos view](#repos), asked when the page opens (bypassing the bridge's cache) and every 10 seconds while it shows: the name, the branch (or the detached commit), then the number of changed files with lines added and removed, or **Clean**, and the commits ahead of and behind the upstream. A click opens the Repos view with that checkout expanded; **See all** opens it as it is. Empty: "No Git checkouts in this folder". The card is absent on a connection without `git`.
- **History.** The project's 8 newest [History](#history) entries (its count is all of them): a closed terminal shows its newest conversation's title, tool, the terminal's name and how many conversations it hosted, with **Resume** for that conversation; a conversation matched by folder and time is marked so; an agent terminal whose conversation is unknown offers only **Open Codex's picker here** (or Claude's), never **Resume**; another that hosted none keeps its first restore choice (**Rerun**, **Open folder**); an outside conversation is marked as such. Resume and restore send the same requests as the History panel (`web/src/conversations.ts`, shared by both). **See all** opens the project's History over the page (Back closes it); History over a home page or a Repos view stays scoped to that project (no **All projects**). The list is asked once when the page opens and again when a terminal opens or closes.

The page uses only existing bridge operations (`projects`, `git` and `conversations`, or `closed` before API minor 7); the bridge's API version is unchanged.

## Repos

A project's **Repos** view (its menu in the sidebar, or `?view=repos&project=<id>`) shows its Git checkouts, read-only: nothing in the web client fetches, pulls, pushes, commits, stages, discards or checks out, and these Git commands never reach the network. The one write is **Add repository**, which clones a new checkout into the project (see [GitHub](#github)). Diffs and history are not shown.

- **Which repositories.** Found automatically, never listed by hand: the project folder itself when it is a checkout, and its direct subfolders that are (by name; hidden folders and symbolic links to folders are skipped), at most 32. Scratch's folder works the same way. A checkout is a directory owned by the bridge's user whose `.git` (a directory, or a file naming a worktree's or submodule's Git directory) is not a symbolic link and is owned by that user; repositories whose metadata another user owns are left out, as in the Terminals table's `repos`.
- **Each checkout.** Its folder name; its branch (or the commit of a detached HEAD); its upstream with how many commits it is ahead and behind that upstream's local ref (as of the last fetch: KelpMux never fetches); its changed files (with staged changes, unstaged changes, untracked and unmerged; each file counted once) and lines added and removed against HEAD (untracked text files included, binary files counted without lines); and its last commit (short hash, subject, relative time). A row expands to its changed files (at most 200 listed, all counted): status letter, path and +/−; clicking one opens it in a Files editor tab (a deleted file cannot be opened). **Show in Files** opens the file browser at the checkout, **New terminal here** starts a terminal there in the project.
- **Marks.** A project's sidebar header shows a quiet mark when any of its checkouts has uncommitted changes (a dot and the number of files) or commits not pushed to its upstream (`↑N`), with a tooltip listing those checkouts. In the file browser, a known checkout folder's second line shows its branch and the same mark instead of its date.
- **Refresh.** The project whose Repos view or [home page](#project-home-page) is shown is asked when the view opens (bypassing the bridge's cache), on **Refresh**, and every 10 seconds while it shows; every project is swept, one at a time and without its file list, once a minute for the marks. Nothing is asked while the page is hidden. The bridge reuses a checkout's facts for 4 seconds while its `HEAD` and index are unchanged.

The bridge's `git {"project": id, "files": bool, "fresh": bool}` (`project` may be `scratch`) returns `{folder, exists, repos, truncated, sampled_at}`; each repo has `path`, `name`, `branch`, `head`, `detached`, `upstream`, `ahead`, `behind`, `files`, `staged`, `unstaged`, `untracked`, `conflicted`, `added`, `removed`, `uncounted`, `last` (`sha`, `subject`, `time`), `changes` (with `files`: `path`, `status`, `staged`, `unstaged`, `added`, `removed`, `from`), `truncated` and `error`. The browser never sends a path: the folder comes from the user configuration. The work runs on the bridge's own Git threads (two, with a queue of four; a request that would wait longer is refused and asked again later), so a slow repository never holds up the terminals' other operations; a project's request has 9 seconds in all (each Git process is killed after 5, or sooner at that deadline, and a checkout it leaves no time for shows so).

**Threat model.** The repositories are the user's own, but their content is not trusted: a cloned repository, an unpacked archive or a checkout an agent touched can carry a `.git/config` (or a file it includes) naming programs that Git runs during commands that look read-only: an fsmonitor hook (`core.fsmonitor`) during `status`, clean, smudge and process filter drivers when it compares a file whose stat data changed, textconv and external diff drivers during `diff`, `gpg.program` when `log.showSignature` is set, hooks when it refreshes the index, and transport programs (`core.sshCommand`, `ext::` URLs, a partial clone's lazy fetch) whenever it reaches a remote. Viewing a repository must never run any of them, so every Git process goes through one hardened runner (`src/native/web_git.rs`):

- a fixed Git binary (`/usr/bin/git`, else `/usr/local/bin/git` or `/bin/git`, never one found in `PATH`) with an argument vector, never a shell, standard input closed, in its own session, killed with its process group after 5 seconds, at the request's deadline or when the bridge ends, with its output read up to fixed limits (1 MiB for `status` and the line counts, beyond which the counts are marked as lower bounds);
- a cleared environment (only `HOME`, `XDG_CONFIG_HOME`, a fixed `PATH` and `LC_ALL=C` kept) with `GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0` and `--no-optional-locks` (so `status` never rewrites the index), `GIT_ALLOW_PROTOCOL` empty and `protocol.allow=never` (no transport at all), `GIT_NO_LAZY_FETCH=1` (Git 2.44 and later; on older Git the transport settings still keep a lazy fetch off the network), and `GIT_CEILING_DIRECTORIES` set to the checkout's parent;
- command-line settings, which win over every configuration file: `core.fsmonitor=false`, `core.hooksPath=/dev/null`, `diff.external=`, `diff.autoRefreshIndex=false`, `log.showSignature=false`, `credential.helper=`, `submodule.recurse=false`, `status.submoduleSummary=false`, and, for every filter driver the configuration names (read first with `git config -z --list`, includes followed), empty `clean`, `smudge` and `process` commands with `required=false` (a configuration naming more than 64 drivers is refused);
- `--no-ext-diff --no-textconv` for the line counts, and `--ignore-submodules=all` for them and `status`, so Git never starts inside a submodule whose configuration was not read;
- only `config --list`, `status --porcelain=v2`, the plumbing `diff-index --numstat` and `diff-files --numstat` (unlike `diff`, which rewrites the index when only stat data changed, even with optional locks off, and with `core.splitIndex` creates `sharedindex` files, they never refresh it) and `log -1`, in a verified checkout root (above);
- only when nobody else can change what configures Git between the listing that names the filter drivers and a later command: every file the repository configuration (local and worktree scope) comes from or would include (`include.path` and `includeIf` targets, even missing or empty ones), `core.attributesFile`, `info/attributes`, the Git directory, a `commondir` target (even in a plain `.git` directory) and alternate object directories must be owned by the user and not writable by group or others, under directories owned by the user or root and not so writable unless sticky (like `/tmp`). Group write is allowed for the user's private group (the umask-002 setup, where no other account is a member or has it as its primary group). Otherwise the checkout shows "skipped: untrusted config". The user's global configuration stays trusted.

Untracked files are read directly to count their lines: only regular files inside the checkout and on its file system (a mount inside it could hang), opened without following symbolic links or blocking, at most 1 MiB each and 200 per checkout, and none once the request's deadline has passed. Rust tests build a repository whose configuration (and an included file) names an fsmonitor, filter drivers, textconv and external diff commands, hooks and a signature program, and check that none of them runs and that the index is untouched; check that touching tracked files without changing them leaves the index bytes, the Git directory's entries and locks unchanged, with and without `core.splitIndex`; and check that writable includes, attributes, `commondir` targets and alternates are refused. The user's global Git configuration (`~/.gitconfig`) is still read, as it is the user's own, for example for global ignore rules; the settings above override it too. As with the file browser, this shows only what the signed-in account can already read.

## GitHub

The web client uses the GitHub access the server already has; it registers no GitHub App and holds no key. Configuration is `[github]` in `config.toml` ([config.md](config.md#github)), edited in the file only, never from the browser.

- **The token.** The bridge reads it from `gh auth token`, `GH_TOKEN`/`GITHUB_TOKEN` in its environment, or `github.token_command` (a program run without a shell or arguments, in its own session, killed after 30 seconds, its first line of output taken, at most 8 KiB read, its error output discarded). It keeps the token in memory for five minutes at most (a failing source is not run again for 30 seconds unless **Test** asks) and sends it only to `api.github.com`, as a `Bearer` header, over HTTPS with no redirects followed and no proxy from the environment. It never reaches the browser, a file, a log, an error message or a Git process. A 401 forgets it. Without a source, or when it fails, the GitHub features say "not signed in" and how to configure one; everything else works as before.
- **Settings → GitHub** shows where the token comes from, the signed-in login (`/user`), the token's scopes (the `X-OAuth-Scopes` header, sent for classic tokens only), the rate limit left, and whether Git has an SSH agent; **Test** reads the token again and checks it.
- **Add repository** (a project's Repos view, beside Refresh, or under "No Git repositories") opens a picker: a free-form clone URL, and the repositories the token can see (`/user/repos` with `affiliation=owner,collaborator,organization_member`, every page up to 2000, cached five minutes, **Refresh** to list again), searchable by name and description, each marked private, archived, fork and with its size. A repository whose name is already a folder of the project shows "In project". Cloning offers the SSH URL (`git@github.com:owner/name.git`) by default and HTTPS on request; clone URLs are built by the browser and the bridge from the owner and name, never taken from GitHub's answer. A repository GitHub reports above 500 MB asks first; above 5 GiB it is refused (the bridge checks again before cloning).
- **Cloning** is `git clone` as the user, with the user's own configuration and credentials (SSH agent, credential helper): nothing is injected or written but the checkout, and the remote stays the URL given. The bridge accepts only `https://host/path` without credentials, `ssh://[user@]host[:port]/path` and `user@host:path`, with letters, digits and `/:._-~@` only, never starting with `-`; the folder is the URL's last segment without `.git`. Git runs with its own environment variables removed (except `GIT_SSH`, `GIT_SSH_COMMAND` and `GIT_SSH_VARIANT`), without `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` (a `gh auth git-credential` helper then uses gh's stored login), no graphical password prompt, `GIT_TERMINAL_PROMPT=0` and no terminal (its own session), `GIT_ALLOW_PROTOCOL` and `protocol.allow=never` with only the URL's transport allowed, `core.hooksPath=/dev/null`, `core.fsmonitor=false`, an empty `init.templateDir`, `submodule.recurse=false` and `--no-recurse-submodules`, `transfer.fsckObjects=true`, Git LFS downloads off (`GIT_LFS_SKIP_SMUDGE=1` and empty `filter.lfs.process` and `filter.lfs.smudge` with `filter.lfs.required=false`; `git lfs pull` fetches the content later) and a low-speed limit, into a hidden sibling folder (`.kelpmux-clone-<name>-<random>`) renamed into `<project folder>/<name>` with `RENAME_NOREPLACE` when complete. An existing target is refused, before and at the rename; a file system without `RENAME_NOREPLACE` is refused too. An `ssh://` user part may not start with `-`. Git is killed with its process group after 15 minutes, on **Cancel** or when the bridge ends (the bridge lives as long as the browser's connection, so a clone does too), and the partial folder is removed. Two clones run at a time. `github.ssh_auth_sock` gives Git an agent when the bridge, started by the web relay's SSH connection, has none. The Repos view shows each running clone with Git's last progress line and **Cancel**, a failed one with Git's last error line, and the new checkout once done.
- **Facts.** For each checkout whose `origin` is on github.com (the `git` operation reports its `owner/name`, never the URL), the Repos row shows its visibility, archived state, default branch, open pull requests and last push, and links to it on GitHub. A repository the token cannot see shows nothing. Facts are cached five minutes; a request fetches at most 16 stale ones within 10 seconds, on the bridge's own thread, one such fetch starts at most every 10 seconds (a request in between is answered from the cache), a bridge fetches at most 500 repositories an hour, and a rate limit pauses GitHub until its reset (five minutes when GitHub does not say).

The operations: `github_status` returns `{enabled, source ("gh" | "env" | "command"), source_label, signed_in, login, name, scopes, rate {limit, remaining, reset}, checked_at, ssh_agent {configured, available}, busy, error, repositories_ready, repository_count, repositories_truncated, clones}` and checks the sign-in on its own thread when it is not known yet; `github_test` forgets the token and checks again; `github_repositories {refresh}` returns the status and `repositories` (`id`, `name`, `full_name`, `ssh_url`, `https_url`, `private`, `archived`, `fork`, `default_branch`, `description`, `size_kib`, `pushed_at`) once listed; `github_clone {project, url}` starts a clone (the folder comes from the configuration, never the browser) and `github_clone_cancel {clone}` stops one, both returning the status, whose `clones` have `id`, `project`, `full_name`, `url`, `path`, `state` (`running`, `done`, `failed`, `cancelled`), `progress` and `error`; `github_state {repos: ["owner/name", …]}` (at most 64) returns `{repos: {slug: facts}, pending, limited}`, answered from the bridge's own thread. Rust tests mock GitHub with a local HTTP server and token programs with shell scripts, and clone from a local repository over HTTP (`tests/github_clone.rs`): the user's configuration applies, its hooks do not run, the remote is the URL given, and failures and cancels leave nothing behind. `node test/github.mjs` covers Settings → GitHub, the picker and the clone flow against a fake bridge (`GITHUB_SCREENSHOTS=dir` saves screenshots).

## History

**History** (the sidebar's tool, `Ctrl-B r`, a project's menu, or `dialog=history`) is one list, newest first, of what can be reopened: closed terminals and previous runs, with every agent conversation each one hosted, and agent conversations started outside KelpMux in a project's folder.

- **Closed terminals.** A closed terminal that hosted exactly one Claude Code or Codex conversation is one row: the conversation's title, with its tool, the terminal's name, project, folder, reason, when it closed and when the conversation ran (first and last seen) as secondary text, **Resume** and a button copying its resume command. One that hosted two or more shows the terminal's name, "N conversations", folder, project, reason and when it closed, with its conversations nested under it, newest first, each with its tool's logo, a title, when it ran, **Resume** and the copy button. A shell that hosted none keeps its own actions: **Rerun** its last program and **Open folder**, through the server's `restore`.
- **Unknown conversations.** A conversation row with **Resume** exists only when its id is known. KelpServer may not have identified a closed agent terminal's conversation (it sees a Codex rollout only while Codex holds it open). The bridge then looks for the one transcript that can be it: the same tool, not a subagent's or reviewer's thread, its folder the terminal's or inside it, first active no later than the close and last active no later than 120 seconds after it, and not hosted by another closed terminal or a live one. When exactly one transcript qualifies, and it is no other such terminal's candidate, it is listed under that terminal (no longer as an outside conversation), marked **matched by folder and time** (its tooltip explains). The records hold no opening time, so an older conversation of the same tool in that folder makes the match ambiguous; nothing is linked then. A terminal left without a conversation offers **Open Codex's picker here** (or **Open Claude's picker here**), which opens a new terminal in its folder and project running `codex resume` (or `claude --resume`) without an id, where you choose the conversation, and **Open folder**.
- **Outside KelpMux.** Conversations whose folder is a project's folder (or inside it, or the Scratch folder) that no closed or live terminal hosted are listed as their own rows, marked **outside KelpMux**, in that project.
- **Resume** opens a new terminal in the conversation's project, in its folder (for a closed terminal's conversation whose folder is gone, the terminal's folder; for an outside one, the project's folder), running `claude --resume <id>` or `codex resume <id>`. A conversation already running in a terminal opens that terminal instead. Resuming does not remove the closed terminal from the list: it may have hosted other conversations.
- **Titles** are the conversation's first user prompt, on one line, at most 80 characters; when it cannot be read, the terminal's name (or "Conversation in <folder>").
- **Per project.** A project's History lists its closed terminals (by their project link, as before) and the outside conversations in its folder; Scratch's lists the terminals of no existing project and the outside conversations in the Scratch folder.

The bridge's `conversations` operation (no parameters) returns `{workspace, entries, external, truncated}`. `entries` are the `closed` entries, each with `conversations`: `kind`, `id`, `cwd`, `folder` (where Resume opens, or `null` when neither folder exists), `title`, `titled` (false when it is the terminal's name), `first_seen` and `last_seen` (epoch seconds, `null` when unknown), and `matched: true` on a conversation linked by folder and time. They come from the closed-session record's `sessions` (every conversation the pane hosted, from KelpCore's history) or, with a KelpServer that records only the latest one, its `kind` and `session_id`, timed from the transcript; with neither, from the match above (Claude Code's candidates are at most 200 transcripts of the folders named after the terminal's folder or one inside it; more and the terminal is left unmatched). `external` lists the outside conversations with the same fields and their `project` (an id, or `scratch`); `truncated` says that a bound below left some out. `new` takes `resume: {"kind": "claude" | "codex", "id": …}` with its `cwd` and `project`: the bridge validates the id (letters, digits, `-` and `_`, at most 128; for Codex the rollout's `session_meta` id, a UUID, which `codex resume` accepts) and builds the command from a fixed table; the browser never sends a command line. `resume: {"kind": …, "picker": true}` without an id opens the agent's picker (`claude --resume`, `codex resume`); an id that is present but invalid is refused, never turned into the picker. With an older bridge the web client lists `closed` as before.

**Transcripts.** The bridge reads the tools' own files, which are internal formats that change, defensively and as little as possible: Claude Code's `$CLAUDE_CONFIG_DIR/projects/<folder with every / and . as ->/<id>.jsonl` (default `~/.claude`), up to the first `user` record whose content is the user's text (not a tool result, a meta, command or caveat record, or a side chain), and Codex's `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<time>-<id>.jsonl` (default `~/.codex`), its first `session_meta` line (id, folder; subagent transcripts are skipped) and its first `user_message` event. Only the title derived from that prompt reaches the browser; nothing else of a transcript is sent, logged or kept. A line that is not JSON or does not have the expected shape is skipped, and a transcript that cannot be read only loses its title: the list never fails because of one. Reading stops after 400 lines or 4 MiB, a line over 1 MiB is skipped unparsed, and transcripts are opened without following symbolic links or blocking and read only when they are regular files owned by the bridge's user, under directories that are not symbolic links and are owned by that user.

**Bounds.** Outside conversations come from transcripts modified in the last 30 days only: for Claude Code the folders named after a project folder or one inside it (at most 4096 entries read per folder, the newest 200 transcripts per project), for Codex the date folders of those 30 days (and tomorrow's, for time zones ahead of UTC; at most 5000 transcripts), at most 200 per project and 1000 in all. The bridge keeps what it parsed in memory and parses a transcript again only when it was replaced, or changed while it still had no title (a first prompt never changes). The work runs on the bridge's own History thread (one listing at a time, two queued), never on the terminals' operations.

## Environments

A project's **Environments** view (its menu in the sidebar, or `?view=envs&project=<id>`; not for Scratch) lists the dev servers and deployments its repositories declare, and starts and stops them on request. [ADR 0005](adr/0005-environments.md) records the design; nothing is ever started on KelpMux's own initiative.

- **Declaring one.** A folder `.kelp/environments/<name>/` with an `environment.toml`, in the project folder or one of its checkouts (found like the [Repos](#repos) view's). A `process` environment runs one long-running command; a `deploy` environment has `up`, `down` and `status` scripts (and optionally `logs`) in that folder:

  ```toml
  # .kelp/environments/web/environment.toml
  kind = "process"
  description = "Vite dev server"
  command = "exec npm run dev -- --host 127.0.0.1 --port $KELP_PORT"
  url = "http://localhost:${KELP_PORT}/"
  [ready]
  http = "http://127.0.0.1:${KELP_PORT}/"
  ```

  ```toml
  # .kelp/environments/staging/environment.toml
  kind = "deploy"
  [scripts]
  up = "up.sh"
  down = "down.sh"
  status = "status.sh"   # prints {"state":"running","url":"https://…","detail":"3 pods ready"}
  ```

  Commands and scripts run in the declaring repository with `KELP_PROJECT`, `KELP_ENV`, `KELP_PROJECT_DIR`, `KELP_SLUG`, `KELP_PORT` (stable per environment, from `environments.ports` in [config.md](config.md)), `KELP_STATE_DIR` (`…/kelpmux/environments/<project>/<env>/`) and `KELP_ENV_DIR`. The repository, the folders, manifest and scripts must be ones only the user can change (the Repos view's rule: not writable by others or another group, under folders nobody else can change), and the environment's own files not symbolic links; anything else, an unknown key or a name declared twice in the project shows the environment as **Invalid** with the reason. Two environments whose slugs are equal (`kelp` + `mux-dev` and `kelp-mux` + `dev`) cannot both start: the second is refused with the other's name.
- **Each row.** The name, kind, state (with the terminals' state marks: **Starting**/**Stopping** as working, **Running** as finished, **Stopped** as idle, **Failed**, **Invalid** as needing attention, and for a deployment not checked since its last action **Not checked**, or its last check with its time, such as "Running · checked 5 min ago"), the declaring repository, the description, the URL (a link, http and https only), the port and the last exit or the status script's detail. **Start** and **Stop** for a process environment; **Deploy**, **Take down** and **Check status** for a deploy one; a terminal button opens the pane running it.
- **Terminals.** A process environment runs in a terminal of the project, `kelpmux env exec` running the command; its scrollback is the log, and the sidebar tags it `env NAME`. Stop sends SIGTERM to the command's process group, waits up to 10 seconds, then closes the terminal. Deploy scripts run in a terminal each, left open with their output until the next action. Starting again closes earlier ended terminals of that environment that sit at their prompt.
- **Refresh.** The shown project's environments are asked when the view opens, after each action, on **Refresh** and every 5 seconds while it shows, never while the page is hidden. Listing runs nothing a repository declares: it reads KelpMux's own records and panes and probes the readiness of process environments that were started. A deploy environment's `status` script runs only on **Check status** (10 seconds at most; a process it leaves behind holding its output is not waited for).
- **Command line.** `kelpmux env list`, `up NAME [--wait]`, `down NAME [--wait]`, `status NAME` and `logs NAME [--lines N]`, in a project's folder (or with `--project ID`), print JSON; they act on the workspace of the terminal they run in (`--workspace` overrides). `list` runs no script; `status NAME` runs a deploy environment's `status` script, as `up` and `down` do once their action is over with `--wait`.

The bridge's `environments {"project": id}` returns `{project, folder, exists, ports, environments, truncated}` (`ports` is the configured range); each environment has `name`, `kind`, `description`, `root`, `repo`, `dir`, `slug`, `port`, `logs`, `state` (`unknown` for a deploy environment not checked since its last action), `detail`, `url`, `pane`, `action`, `error` and `checked` (a deploy environment's last check: `state`, `url`, `detail`, `at` in epoch seconds, or `null`). `environment_check {project, name}` runs that environment's `status` script and returns its entry; it is the only operation that runs one. `environment_start` and `environment_stop` take `{project, name, request}` (a fresh request identity per click, letters, digits, `-` and `_`) and return the pane and new state; a refusal (already running, a busy pane, an invalid manifest, a slug another environment holds) is the bridge's error. `environment_panes` returns `{panes: {pane id: {project, env, action}}}` for the sidebar's tags. The browser never sends a path or a command. These run on the bridge's environment threads (three at most; another request is refused until one ends), never on the terminals' operations.

## Layout

On a desktop or tablet the left sidebar is the only navigation; there is no top bar and no status bar. The main area shows the focused terminal (with the [side panel](#files) to its right when a file is open there; its header has the number, state, title, folder, a **TUI** or **Other browser** badge when that client holds its input and size, and the files button, notifications bell, Find, Park, Open in a window and Close), the live grid, the file browser or an open file. From top to bottom the sidebar holds:

- KelpMux, the **DEV** badge on a development relay, and the state counts (click one to jump to the next terminal in that state), with no separator line before the tabs.
- The terminal tabs, directly under it in this browser's order, with no section header. Each tab is a row with the terminal's number, state, provider, title and folder on two lines. Clicking a tab opens that terminal alone, also from the grid; the tab of the terminal shown alone is selected, and in the grid or the Files view no tab is. The tabs have no colour stripe; a thin rule separates each terminal from the next. A tab with unread notifications that is not shown alone shows a ringing bell (with the count when there are several), as does its grid tile header.
- **New terminal**, right under the tabs, like the TUI's "+ New tab" row: the **+** and its label centred between two rules in the accent colour, with some room above and below it (only the **+** between two short rules when folded); its tooltip gives the shortcut, `Ctrl-B Enter`. Then the collapsible **Parked** subsection.
- At the bottom, right above the vitals, two plain entries for the other views, with their icon in the tabs' number column (only the icon when folded), no count and no chevron. **Grid** (a 2×2 grid icon; its tooltip gives `Ctrl-B g` and `Alt+Tab`) opens the live grid and is selected while it shows; phones have no grid and no Grid entry. The grid is one read-only page for monitoring: it shows every live (unparked) terminal at once, in columns and rows chosen to fit them all in the available area with tiles close to a terminal's shape, re-laid out as terminals come and go, with no paging. It has no focused tile and takes no input; each tile shows its terminal's state, badges, unread bell, title and folder above its live screen, and a click anywhere on a tile opens that terminal alone. **Files** (a folder icon), when the connection offers files, opens the [file browser](#files) and is selected while the Files view shows (the browser or an open file). The sidebar has no file tree: the open files are tabs in the Files view. These entries stay in place while the tabs scroll above them.
- The vitals, drawn like the TUI's sidebar status: CPU (green) and RAM (purple) meters with their percentages, then the first two disks as pies filled by usage like the TUI's `○ ◔ ◑ ◕ ●` (yellow, red from 90 % used), each with its mount point and percentage in a tooltip. The colours are the TUI's in dark mode and darker shades of the same hues in light mode. Clicking the vitals opens System status.
- The tools in two columns, like the TUI's sidebar buttons, with short labels: **Terminals** (with a list icon, unlike the Grid entry's grid icon), **History** (closed terminals and their conversations), **Search** and **Help**. Each tooltip gives the full name and shortcut. They scroll on their own when the window is short, so the tabs keep most of the height; with ten tabs they fit an 800 pixel tall window without scrolling.
- At the very bottom, the account (the user name) and its **Settings** (`Ctrl-B ,`).

A narrow fold handle sits vertically centred on the sidebar's edge; the folded rail keeps the numbers, state marks and unread bells, the tools' icons in one column, compact vitals (CPU and RAM percentages and the disk pies) and the account's initial. Clicking the edge also folds it and dragging it resizes. There is no full width mode: the folded rail is the smallest sidebar. The workspace name is not shown anywhere in the main interface: one relay serves one workspace, so the sign-in screen names the user and the relay's host instead, the **Workspace not running** screen names the workspace it would start, and History names a workspace only on an entry that came from another one.

## Keyboard

`Ctrl-B` is the browser's prefix, and the keys after it follow the TUI's default bindings wherever the browser has the same action: `Enter` new terminal, `Tab`/`Shift+Tab` next/previous terminal, `1`…`9` terminal by number, `g`/`e` live grid, `h`/`k` or left/up arrows previous terminal and `j`/`l` or right/down arrows next terminal, `N` next question, `P` next completion, `o` the Terminals table, `a` the same table showing agents, `!` agents needing attention, `n` finished agents, `b` the focused terminal's notifications, `r` History, `z` reopen the last closed terminal, `/` search terminal history, `[` scroll mode, `Space` selection mode, `p` park, `u` parked terminals, `s` move, `x` close (confirmed), `,` settings, `?` help, `d` disconnect, and `Ctrl-B` twice sends `Ctrl-B` to the terminal. Every key that opens a terminal (a number, next or previous, next question or completion, reopen) shows it alone, leaving the grid; in the read-only grid the keys that act on the focused terminal (`b`, `[`, `Space`, `p`, `s`, `x`, `Ctrl-B` twice, `Ctrl/Cmd+F`) do nothing. Outside the prefix, `Alt+1`…`Alt+0` open terminals 1–10, `Alt+Tab` or `Ctrl/Cmd+Shift+G` toggle one terminal / live grid, and `Ctrl/Cmd+F` finds in the focused terminal. In scroll mode, `PgUp`/`PgDn`, `Ctrl-U`/`Ctrl-D`, `Ctrl-B`/`Ctrl-F`, `j`/`k` or arrows scroll, `g`/`G` jump to the oldest line or the live screen, `Space` or `v` switches to selection, and `Esc` or `q` leaves. In selection mode, `h`/`j`/`k`/`l` or arrows move the cursor (scrolling at the edges), `0`/`$` line start and end, `w`/`b` eight columns, `Space`/`v` set or clear the anchor, `y` or `Enter` copy and leave, `Esc` or `q` leave. Every other key goes to the terminal shown on its own (never to a grid tile) with full modifier and Kitty keyboard-protocol support. Settings → Keyboard and Help list these bindings. The TUI's own bindings and configuration file are unchanged; custom TUI bindings are not read by the browser.

The mouse covers the rest: click a sidebar row to open that terminal alone or **Grid** at the bottom of the sidebar to open the grid, click anywhere on a grid tile to open that terminal alone, drag rows (or grid tiles) to reorder, right-click a row or tile for its menu (open, open in a window, find, move up/down, park/unpark, notifications, upload files, browse files here, close), drop files onto the terminal shown on its own to upload them, Cmd/Ctrl-click a file path printed in it to open the file beside it ([path links](#files)), middle-click a row to close it, click the sidebar's state counts to jump to the next terminal in that state, click the fold handle or the sidebar's edge to fold it, and drag the edge to resize it.

## Navigation

The page URL names the place shown, so the browser's Back and Forward (its buttons, a mouse's back and forward buttons, `Alt+←`/`Alt+→` outside a terminal that takes them, a two-finger swipe on a Mac, a phone's back gesture) move through the places visited, and a reload, a bookmark or a link opens the same place. Everything stays in one page: Back and Forward never reload it and never leave a terminal's session. `web/src/navigation.ts` encodes, decodes and decides; `main.tsx` mirrors its state into the history after every change and applies the location of each `popstate`.

| Place | URL query |
| --- | --- |
| One terminal on its own | `?view=terminal&terminal=<pane id>` |
| …with a file in the [side panel](#files) | `?view=terminal&terminal=<pane id>&side=<path>[&line=<n>]` |
| The live grid | `?view=grid` |
| The file browser at a folder | `?view=files&dir=<folder>` |
| An open file in the main area | `?view=files&file=<path>[&line=<n>]` |
| A phone's terminal list | `?view=home` |
| A panel over any of them | `…&dialog=<settings, help, terminals, search, history, parked, move, status or notifications>[&of=<pane id>]` |
| A project's grid, files or History | `…&project=<project id>` after `?view=grid`, `?view=files…` or `dialog=history` |
| A project's [Repos view](#repos) | `?view=repos&project=<project id>` |
| A project's [home page](#project-home-page) | `?view=project&project=<project id>` |
| A project's [Environments view](#environments) | `?view=envs&project=<project id>` |

A terminal is named by its server pane id, which stays the same while terminals are reordered, parked or renumbered, never by its position. Paths keep `/` and `~` readable and escape the rest. `of` is the terminal whose notifications the panel shows; `line` is where the file opened (from a path link). `project` names the [project](#projects) a grid, file browser, Repos view, home page or History shows; an unknown project shows every project instead, with a toast, replacing the entry. The former `dialog=closed` (before History) opens History and is rewritten as `dialog=history`. Parameters the client does not own are kept: KelpHub-era links keep `workspace` and `scratch` (their `project` is read as this client's and falls back the same way), and their `view=terminals` (with or without `terminal`) opens that terminal or the grid, `view=files` the browser, and `view=overview` or `view=events` the client's own default. `pane` is reserved for windows opened with **Open in a window**, which show one terminal and keep no history; each window or tab has its own history, and the shared connection is unaffected.

Which changes add an entry:

- **Push**: every move to another place, whether from the sidebar, a grid tile, a toast, a panel's list or a keyboard shortcut (`Ctrl-B` digits, `Tab`, `g`, `N`, `Alt+digit`, `Alt+Tab`, …), and opening a panel that covers the application (Settings, Help, Terminals, Search, History, Parked, Move, System status, a terminal's notifications), so Back closes it, as phones expect. Each folder opened in the file browser is a place: clicking a folder in a column (or a breadcrumb) pushes, and the deepest folder shown is the `dir` in the URL, from which a deep link builds the columns from the root down.
- **Back instead of push**: closing a panel (its close button, `Esc`, a click outside) returns to the entry under it rather than adding one, so the panel can be reopened with Forward and Back never shows the same place twice. Leaving a panel for another place (a terminal opened from the Terminals table or Search) takes the panel's entry, so Back returns to where the panel was opened.
- **Replace**: the first location after loading or reconnecting, a panel swapped for another, another line in the same file, and changes nobody asked for: a terminal that closed or was parked while shown (its next terminal takes the entry), the browser's `~` or a symbolic link read as its real folder, the file browser's keyboard moves and a file selected in an earlier column (which closes the deeper columns), a file closed, a phone turned into a tablet layout, and every fallback below.
- **Nothing**: selecting the place already shown, and everything transient: menus, tooltips, toasts, the find bar, confirmations, the upload review, security key prompts, scrolling, selections and Settings' own sections.

A loaded URL is applied once the client is signed in, the terminals are listed and the files capability is known; until then the URL is left untouched. A terminal that no longer exists falls back to the grid (a phone's list) with a toast, a file that no longer exists to its folder in the browser, a folder to the browser at it, files on a connection without them stay where the client is; each fallback replaces the entry. Going back to a place whose terminal has since closed falls back the same way. A file with unsaved changes in the side panel stays there when Back or Forward goes to a place without it (its buffer lives in the panel's editor); a file without changes becomes a tab in the Files view. Switching tabs in the Files view (the browser's tab included) is a move and pushes an entry; closing the tab shown replaces its entry with the tab shown next (the neighbour, or the browser). Each entry's `history.state` carries `{ kelpmux: { v: 1, overlay } }`: `overlay` marks a panel pushed over the entry below, and the version lets a later format migrate older entries (the URL alone is enough to restore a place).

## Phones and tablets

The same client adapts to iPhone and iPad (Safari first; [ADR 0003](adr/0003-web-client-in-kelpmux.md#addendum-phones-and-tablets) records the decisions). The layout follows the viewport and the primary pointer (`web/src/device.ts`): a touch screen whose short side is under 600 CSS pixels is a **phone** (every iPhone, both orientations), any other touch screen a **tablet** (every iPad), and a mouse-driven window narrower than 600 pixels also gets the phone layout.

- **Phone.** The home screen is the terminal list: the sidebar's content (state counts, the terminals, **New terminal** and parked terminals, the **Files** entry, then the vitals, the tools in two columns and the account with settings) at full width, scrolling as one list. Tapping a terminal opens it full screen; **‹ Terminals** returns to the list, the bell opens the terminal's notifications (ringing, with the count, while some are unread), and **⋯** opens the terminal's menu (find, move, park, notifications, upload files, browse files here, close). There is no grid and no Grid entry. **Files** in the list opens the file browser full screen, one folder at a time, and a file opened from it the editor, each with **‹** back to the list. The terminal shown is sized to the phone through the normal per-pane lease, exactly as a desktop browser's focused terminal is.
- **Tablet.** The desktop layout, sidebar and grid, with larger tap targets. Landscape and portrait are both supported; in portrait the sidebar starts folded each time the tablet turns to portrait (that fold is not saved), and the fold handle on the sidebar's edge unfolds it. Landscape uses the saved sidebar preference.
- **Touch on a terminal.** A tap selects the terminal and takes its lease without showing the keyboard (an application that requested mouse reporting receives the tap as a click; a link opens). One finger dragged up or down scrolls the history, as the wheel does. A long press selects the word under the finger; dragging extends the selection, and lifting copies it. Pinch zoom is not supported. Sidebar rows scroll on touch instead of reordering; their **⋯** menu has Move up / Move down.
- **Keyboard.** Opening a terminal never brings up the on-screen keyboard: reading is the default. The key bar under the terminal has **Input**, which shows the keyboard (and becomes a hide-keyboard button while it is up); tapping any key on the bar also enters input mode. The bar holds Esc, Tab, Ctrl, the arrows, `^B`, Paste, Enter, Yes and No. Ctrl is sticky: it applies to the next key from the bar or the keyboard, then releases. `^B` arms the KelpMux prefix, so the next key typed is a prefix key as on a desktop. Paste reads the clipboard (Safari asks first). Yes and No send `1` and Escape to Claude Code, whose questions are numbered menus, and `y` and `n` to anything else; they do not add Enter. The bar follows the `visualViewport`, so it stays directly above the iOS keyboard, and the layout respects the safe-area insets. These rules apply to the iPad too.
- **Hardware keyboard.** Settings → Keyboard → **Hardware keyboard** (shown on touch devices, saved per browser) chooses how a physical keyboard (an iPad's Magic Keyboard, a Bluetooth keyboard) reaches the terminal shown. **Auto**, the default: terminals still open for reading, and the first key typed on a hardware keyboard enters input mode and is delivered to the terminal, not lost. **On**: terminals open in input mode, ready for the hardware keyboard, without bringing up the on-screen keyboard. **Off**: tap Input or a key bar key first, as before. A hardware key is recognised because iPadOS sends it to the page while no text field has focus, which the on-screen keyboard cannot do; Cmd shortcuts, modifier keys pressed alone and the app's own shortcuts (`Ctrl-B` and the others) are left alone. Input mode entered from the hardware keyboard focuses the terminal's input with `inputmode="none"`, so iOS does not show the on-screen keyboard; the Input control and the key bar still show it. With On, Safari may refuse to focus the input when the terminal opens without a tap; the first key typed then enters input mode as with Auto. The setting applies to phones too.
- **Installable web app.** `manifest.webmanifest` (standalone display with the window controls overlay preferred on desktop, theme colours, 192 and 512 pixel icons, a maskable icon) plus the iOS meta tags and a 180 pixel `apple-touch-icon` let Safari's **Add to Home Screen** install KelpMux as its own app. There is no service worker: nothing is cached offline (the client needs its relay anyway), and the cross-origin-isolation and asset headers stay exactly as the relay sets them. There are no push notifications. The PNG icons are rendered from `web/public/icons/icon.svg` by `web/scripts/render-icons.mjs` and committed.
- **Integrated title bar on desktop.** The manifest also sets `display_override: ["window-controls-overlay"]`, so an app installed from desktop Chrome or Edge can hide the native title bar (the chevron in the app's title bar toggles it). The page then draws its own thin title bar across the window (`TitleBar.tsx`, `styles/titlebar.css`): the KelpMux mark and name, then the place shown (the terminal's title, Grid, `Files — <folder>` or the open file's name), clear of the window controls on either side through the `titlebar-area-*` environment variables, and at least 32 pixels tall. It is the window's drag region and holds nothing clickable; the location gives way first when the window is narrow. The sidebar's header drops its KelpMux mark there (the bar carries it), and the sidebar, the terminals, dialogs and toasts start below the bar. The bar's background is the theme's background, which the client also sets as `theme-color`, so Chrome paints the window controls in the same colour in every theme. In a browser tab, the standalone fallback with the overlay toggled off, Safari and phones, nothing changes. Playwright cannot enter this display mode; `test/sidebar.mjs` lays the bar out with its rules forced on.
- **Sign-in** is the same YubiKey WebAuthn flow, over NFC or USB-C; iCloud Keychain passkeys are not supported as SSH keys. The sign-in and key-registration screens fit a phone and scroll instead of overflowing.

## Reusable terminal component

The terminal layer is KelpCore's [`@kelpcore/web`](https://github.com/joanfabregat/kelpcore/tree/main/web) package, moved there from this repository's `web/src/terminal/` at `7179aa3` ([KelpCore ADR 0003](https://github.com/joanfabregat/kelpcore/blob/main/docs/adr/0003-kelpcore-shared-repository.md)). KelpMux and another web application (KelpHub) consume it at a pinned KelpCore commit: SSH/WebAuthn connection and key discovery, the SharedWorker session broker, WASM client-core loading, the WebGL/Canvas renderer, keyboard, mouse and wheel encoding, the touch key bar encoding and input mode (`touch-keys.ts`), the upload protocol, limit checks and path quoting (`uploads.ts`), selection and copy, the screen cache, grid column layout, the `Terminal`/`TerminalTile` React components and pane find. It imports no application code. It is not published to an npm registry: `web/package.json` depends on `"@kelpcore/web": "github:joanfabregat/kelpcore#<commit>"`, a TypeScript source package whose files are imported with their extension (`@kelpcore/web/Terminal.tsx`, `@kelpcore/web/terminal.css`; its `exports` maps `./*` to `web/src/*`). Its `files/` modules hold the file request client (`api.ts`), path helpers (`paths.ts`), the open-document model and language detection (`model.ts`, `languages.ts`) and the lazily loaded CodeMirror 6 `TextEditor` with its theme (`editor.tsx`, `theme.ts`), derived from KelpHub's; their CodeMirror and Lezer packages are dependencies of `@kelpcore/web`, so KelpMux gets them through it. Pin the same KelpCore commit as the `Cargo.toml` revision that builds `client-core.wasm`.

## Current limits

- The Repos view is read-only and shows no diffs or history. It finds checkouts only in a project's folder and its direct subfolders (at most 32), lists at most 200 changed files per checkout, and its upstream counts are as of the last fetch made elsewhere. In the file browser only checkouts of projects (Scratch included) show their branch.
- The file browser and editor edit one file at a time per view: no multi-select, split editors, diff, or file search across folders. Text files over 2 MiB open read-only; moving or renaming across file systems, and trashing a file on a file system other than the trash's, fail with the server's reason (delete instead).
- The grid shows every live terminal on one page. It streams as many terminals as the server allows one connection (Welcome `limits`, 64 with `stream-limits`, ten before), less two kept for popup windows; with an older server, tiles beyond that show their header without content.
- Panes cannot be renamed or split from the web: KelpServer has no rename operation, and its layout is automatic. Pane titles follow the running program.
- History search uses the server's bounded literal search (64 matches per terminal); the Search dialog searches at most 32 terminals and shows at most 200 hits. Older history pages are plain text.
- Restoring a closed terminal from the browser does not remove it from the TUI's Closed list (the server owns that file); restoring an agent conversation that is already open opens the existing terminal instead.
- Notification state for a pane is matched by pane and process ID; the browser does not see the server's run identifier, so a notification from a previous server run whose pane and process IDs both recur could be shown until it is read.
- Real hardware-key and Safari behaviour need manual acceptance; automated tests use virtual authenticators only where noted.
- Phones and tablets are tested with Playwright device emulation only. The on-screen keyboard, the key bar's position above it, safe areas, Add to Home Screen, NFC and USB-C security keys and the connected phone and tablet layouts need acceptance on a real iPhone and iPad. On iOS an installed web app has its own storage, separate from Safari's: its first sign-in asks the authenticator which key to use, as a new browser does, and its layout and settings start fresh. Closing it, or iOS suspending it in the background, ends the SSH connection like closing a tab; terminals keep running.
