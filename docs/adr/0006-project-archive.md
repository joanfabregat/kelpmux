# ADR 0006: Project status, archive, restore and delete

- Status: Accepted (first version).
- Date: 2026-11-24 (America/Los_Angeles).
- Related: [ADR 0003](0003-web-client-in-kelpmux.md), [ADR 0005](0005-environments.md), [configuration reference](../config.md#project-status-archive-restore-and-delete), [web client guide](../web.md#archive). Brings KelpHub's "safe removal" roadmap item to KelpMux.

## Context

Projects pile up on a development machine: finished client work, experiments, old checkouts with gigabytes of build output. Deleting a project folder by hand loses whatever was never pushed (a stash, a local branch, notes outside any repository), and keeping everything fills the disk. A project should be able to leave the machine safely and come back later, and deleting one should say what would be lost first.

KelpMux runs as the user, on a machine that usually has a cloud identity of its own (jbox: a GCE service account). It must not become a credential broker, must not send tokens to the browser, and must never delete outside the folders it manages.

## Decision

1. **Status.** `[[project]]` gains `status = "active" | "paused" | "archived"` (default active). Paused only dims the project. Archived means the folder was archived and removed; the project stays in `config.toml` with an `[project.archive]` record (backend, bucket, object, size, SHA-256, CRC32C, time) so it can be restored, and is listed in a folded **Archived** sidebar group.
2. **Safe-removal check** (`src/native/removal.rs`), reusable by later features (removing a checkout or a worktree). For each Git checkout of the project (the Repos view's discovery) it reports uncommitted changes, untracked non-ignored files, stashes, local branches with commits on no remote-tracking branch, branches without an upstream, a detached HEAD with commits on no branch or remote, commits reachable only from tags, notes, other refs or another worktree's HEAD (`rev-list --all --not --remotes --branches HEAD`, the stash excluded), and linked worktrees outside the folder (`worktree list`), a blocker for a deletion since the folder holds their repository. The repositories found inside a checkout are inspected the same way: checked-out submodules (from `.gitmodules` and the index's gitlinks), repositories inside its ignored or untracked folders (searched without following links or leaving the file system, within the same bounds as the walk), and linked worktrees inside the folder; a submodule repository in `.git/modules` that no checked-out submodule uses, a repository that cannot be inspected, or a search cut short is an `unchecked` finding. Outside the checkouts it counts files and bytes, and reports ignored files, special files, nested repositories the discovery does not inspect, unreadable folders and mount points. Git runs only through the hardened runner of `web_git` (no hooks, filters, fsmonitor, pager, network or lazy fetch; bounded time and output). Each finding has a severity. For a deletion, Git findings are blockers; for an archive they are warnings, because `.git` is archived too, and the message says those commits then exist only in the archive. The check has a fingerprint over its findings; an archive or deletion needs the fingerprint the user confirmed and runs the check again first, and an archive runs it once more just before removing the folder. Any difference aborts.
3. **Archive format: tar.gz written in process**, streamed to a private temporary file with the `tar` crate (GNU headers for long names) and `flate2` (pure-Rust backend), while SHA-256 (`ring`, already a dependency) and CRC32C (a table implementation in KelpMux) are computed. Symbolic links are stored as links, never followed; sockets, FIFOs and devices are skipped and listed; modes and modification times are kept (a restore drops set-id and sticky bits); a folder on another file system stops the archive. Files are opened with `O_NOFOLLOW` and checked to be the entry that was listed. The folder's own mode is stored as the archive's first entry, `./`, and given back to the restored folder (0700 for an archive without it).
4. **Storage: Google Cloud Storage's JSON API**, through `ureq` (already a dependency) with no proxy, redirects off, HTTPS only (the metadata server excepted), and requests only to `storage.googleapis.com` and `metadata.google.internal`. Upload is resumable (8 MiB chunks, resumed from the server's committed offset after a transient failure, the session deleted on failure) to a new object `<prefix>/<project id>/<UTC time>.tar.gz` with `ifGenerationMatch=0` (never over another object). The object's metadata holds the project's id, name and folder, KelpMux's version, the entry and unpacked byte counts and the SHA-256. The CRC32C is given when the upload starts, so Cloud Storage refuses a corrupted upload; KelpMux then reads the object back and compares size, CRC32C and SHA-256 metadata. MD5 is not used: composite-safe CRC32C is what Cloud Storage guarantees for every object, and SHA-256 covers the content end to end.
5. **Credentials.** The access token comes from the GCE metadata server (the VM's service account) or, when set, from `archive.token_command` (a program run without a shell or arguments, as `github.token_command`). It is kept in memory for at most 45 minutes, sent only to Cloud Storage, and never logged, written or sent to the browser; errors name the source, never the token. `config.toml` holds no secret.
6. **Removal.** Only after the verification and the passing check, the configuration records the archive and `status = "archived"`, then the folder is renamed to a hidden sibling `.kelpmux-removing-<random>` (`renameat2` with `RENAME_NOREPLACE`) and deleted with `remove_dir_all`, which never follows links; read-only folders of the user are made writable through an `O_PATH | O_NOFOLLOW` descriptor. The guards refuse a folder that is a link, not owned by the user, not strictly inside `files.root` or `files.extra_roots`, the projects folder, the Scratch folder, the home folder, `/`, a folder containing another project, the configuration or KelpMux's state, or one with a mount point below it. If removal fails, the status goes back and the error says where what is left is.
7. **Restore.** The chosen object (the recorded one by default, otherwise one under `<prefix>/<project id>/`) is downloaded to a private temporary file; its CRC32C must equal Cloud Storage's and its SHA-256 the object's metadata (and the record's). The download stops at the object's size. It is unpacked into a fresh private folder beside the destination, never past the entries and bytes counted at packing (in the record and the object's metadata; at most 64 times the archive's size plus 1 GiB and 10 million entries for an archive without them), with the decompressed stream bounded too and 256 MiB kept free on the disk (checked before unpacking), refusing absolute paths, `..`, hard links, special files, a member twice and any path through a symbolic link (each component is created with `O_NOFOLLOW` and checked to be a real folder), then renamed into place without replacing anything. The destination is the original folder, which must not exist, or a new folder inside `projects.base`. The status becomes active; the record and the object stay.
8. **Delete.** Deleting the folder without an archive needs the passing check and, in the web client, the project's name typed; it can also remove the project from the configuration. "Remove from KelpMux" removes only the configuration entry.
9. **Jobs.** Archive, restore and delete are jobs run by a `kelpmux project … --job ID` process the bridge starts detached (its own session, no stdio), so a closed browser or SSH connection does not stop one. An exclusive `flock` on `$XDG_STATE_HOME/kelpmux/archive/<project>.lock` allows one job per project across bridges and the CLI; the job's state is `<project>.json` there, written atomically at most every 250 ms, and a cancel request is `<project>.cancel` holding the job id, honoured until removal starts. A job whose process ended without finishing is shown as failed. Memory stays bounded: everything streams through files and fixed buffers.
10. **Interfaces.** The bridge adds `project_status`, `project_check_removal`, `project_archive`, `project_restore`, `project_delete_folder`, `archive_jobs`, `archive_cancel`, `archive_list`, `archive_status` and `archive_test` (API version 3, minor 11); checks, listings and the test run on threads of their own (two at most). Archive and delete are refused while the project has open terminals. The CLI is `kelpmux project status | check-removal | archive | archives | restore | delete | jobs | cancel | archive-test`, printing JSON. The web client adds the project menu entries, the check and progress dialog, the Archived group, Restore on the project page and Settings, **Archive** with a Test that writes and deletes an object under `<prefix>/.kelpmux-test/`.
11. **Backends.** Only `backend = "gcs"` exists. The archive flow uses the store through a handful of operations (upload with a checksum, read an object's details, list, download, delete), so an S3-compatible backend can be added behind the same flow; `"s3"` is reserved and refused for now (roadmap).

## Consequences

- A project can leave the machine with its uncommitted work and come back byte for byte, with links, modes and times; nothing is deleted until the archive is verified in the bucket.
- The bucket holds whole copies of the folders, including ignored files such as `.env`: its access must be as restricted as the machine's. Bucket retention and lifecycle rules are the user's choice; KelpMux never deletes an archive.
- New dependencies: `tar` 0.4.46 and its dependency `filetime` 0.2.30 (MIT or Apache-2.0); `flate2` and `ring` were already in the lock file.
- A check is a snapshot: the user confirms what it found, and the fingerprint stops an action when the folder changed since; changes made during an archive after the last check are not caught beyond the change-time comparison.
