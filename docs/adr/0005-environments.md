# ADR 0005: Environments

- Status: Accepted (first version).
- Date: 2026-11-24 (America/Los_Angeles).
- Related: [ADR 0003](0003-web-client-in-kelpmux.md), [web client guide](../web.md#environments), [configuration reference](../config.md). Adapted from KelpHub ADR 0004 (project configuration and environments), whose Environments section this decision brings to KelpMux.

## Context

A project's repositories usually come with ways to run them: a dev server on a port, a staging deployment brought up and down by scripts. Agents and people start these by hand in a terminal, pick ports that collide between projects, forget which terminal holds which server, and cannot tell from the sidebar whether staging is up. KelpHub's ADR 0004 designed **environments** for this around its workspaces. KelpMux has projects (a folder with zero or more Git checkouts, ADR 0003 addenda) and no workspaces in that sense, so the design is adapted: one instance of each environment per project.

KelpMux must stay a terminal application: it supervises nothing outside KelpServer panes, owns no containers, and never starts anything on its own.

## Decision

1. **Declaration.** An environment is a folder `.kelp/environments/<name>/` holding `environment.toml` and its scripts, in the project folder or in any of its Git checkouts (the Repos view's discovery: the folder and its direct subfolders that are checkouts). Names are lowercase letters, digits and `-` (not first or last), at most 32 characters. The same name declared in two places of one project is an error shown on every copy, never a silent precedence. At most 64 environments per project.
2. **Trust.** Discovery applies the Repos view's rule (`web_git::trusted_path`): the declaring repository, every directory from its `.kelp` down, the manifest and every script must be owned by the user and not writable by others or by any group but the user's private one, under folders owned by the user or root that nobody else can change (unless sticky); the environment's folders, manifest and scripts must not be symbolic links, and scripts must be executable regular files inside the environment's folder. A declaration that fails these checks, or a manifest that fails validation, is listed as **invalid** with its problem and cannot be started. These rules keep other accounts out; they do not make a repository's content trustworthy, which decision 7 handles.
3. **Manifest format: TOML.** `environment.toml`, parsed strictly with the `toml_edit` crate KelpMux already uses for `config.toml`: unknown keys, wrong types, keys of the other kind and missing required keys are errors. KelpHub's design used YAML; no YAML crate is in `Cargo.lock`, and adding one for a dozen keys is not worth a new dependency, so TOML matches the user configuration instead.
4. **Kinds.**
   - `process`: `command`, a long-running program given as one string run by `/bin/sh -c` (so `exec`, pipes and `&&` work as in a terminal). Readiness is a TCP connect to `KELP_PORT` by default, or `[ready] port = N`, or `[ready] http = "http://127.0.0.1:${KELP_PORT}/health"` (loopback only; any HTTP response under 500 counts). An optional `url` is the link shown. The state is **starting** until ready, **running** once ready, **stopped** after a clean exit or Stop, **failed** after a non-zero exit or a signal.
   - `deploy`: `[scripts] up`, `down` and `status`, and optionally `logs`, each a file in the environment's folder. `up` and `down` exit when done. `status` prints one JSON object `{"state": "running" | "stopped" | "failed", "url": …, "detail": …}` on standard output within 10 seconds; anything else reads as **failed** with the reason. While `up` or `down` runs, the state is **starting** or **stopping**; otherwise it is **unknown** (with the last explicit check and its time) until `status` runs on request, or **failed** when an `up` or `down` failed since that check.
5. **Variables.** Every command and script gets `KELP_PROJECT` (the project id), `KELP_ENV` (the name), `KELP_PROJECT_DIR` (the project folder), `KELP_SLUG` (`<project>-<env>` as a DNS label, at most 63 characters, shortened with a hash suffix; see decision 6), `KELP_PORT`, `KELP_STATE_DIR` (`$XDG_STATE_HOME/kelpmux/environments/<project>/<env>/`, default under `~/.local/state`, created private; two levels because two pairs can share a slug) and `KELP_ENV_DIR` (the environment's folder). Commands run in the repository that declares the environment. `${KELP_PORT}` and `${KELP_SLUG}` are substituted in `url` and `ready.http`.
6. **Ports and slugs.** `KELP_PORT` is stable per (project, environment): allocated once from `environments.ports` in `config.toml` (`"FIRST-LAST"`, default `"41000-41999"`), skipping ports already allocated and ports busy at allocation, and kept in `$XDG_STATE_HOME/kelpmux/environments/ports.json`, written under a `flock` with an atomic replace. A port stays allocated after the range changes or the environment disappears; ports are not reclaimed in this version. The same record holds each pair's slug: `kelp` + `mux-dev` and `kelp-mux` + `dev` are both `kelp-mux-dev`, so a pair whose slug another pair already holds is refused at Start with an error naming that pair (rename one of them), and `KELP_SLUG` always names one environment.
7. **Explicit only, and listing runs nothing.** KelpMux never starts, restarts, stops or checks an environment on its own: not at startup, not when a workspace server restarts, not when a process exits, and not when a project is listed or a view opens. A freshly cloned repository passes the trust rules, so its scripts are arbitrary code: they run only on a request naming that environment. Only the web client's **Start**/**Stop** (or **Deploy**/**Take down**) and **Check status**, and `kelpmux env up|down|status NAME`, act; `up` and `down` with `--wait` check a deploy environment's status once their action is over.
8. **Supervision in KelpServer panes.** A `process` environment runs in a dedicated pane of the workspace's KelpServer, linked to the project like any of its terminals and recorded as an environment pane (`environments.json` in the workspace's state folder, keyed by server epoch and pane). The pane runs `kelpmux env exec`, which re-reads and re-validates the manifest, sets the variables, runs the command in its own process group, and records the run and how it ended in `run.json` in `KELP_STATE_DIR`. The pane's scrollback is the log; anyone can open the terminal, watch it and type into it. Stop signals the runner's process group (SIGTERM, verified by its command line and run id), waits up to 10 seconds for the exit record, then closes the pane, which ends whatever remains. `deploy` scripts `up` and `down` run the same way in short-lived panes whose output stays readable until the next action; `status` and `logs` run in the bridge or CLI, in their own process group, killed after 10 seconds, with bounded output. KelpServer stays generic: it learns nothing about environments.
9. **Polling, not watching.** The bridge works out each environment's state when asked (`environments`) from what KelpMux itself recorded and observes: the runner's record, the pane's presence and, for a process environment that was started, the loopback readiness probe. It never runs a script to list. The web client asks every 5 seconds only while a project's Environments view is visible; a deploy environment's `status` script runs only on **Check status** (`environment_check`) or `kelpmux env status NAME`, and its answer is kept (`check.json` in `KELP_STATE_DIR`) and shown with its time until the next check.
10. **Interfaces.** The bridge adds `environments`, `environment_start`, `environment_stop`, `environment_check` and `environment_panes` (API version 3, minor 8), on their own threads (at most three at once, each slot given back however the thread ends) so a slow status script never holds up the terminals. The CLI is `kelpmux env list | up NAME [--wait] | down NAME [--wait] | status NAME | logs NAME [--lines N]`, printing JSON, with the project inferred from the current directory (`--project` overrides) and the workspace from the terminal it runs in; `list` runs no script. The web client shows a project's environments at `?view=envs&project=<id>`, from the project's menu, with a reusable `EnvironmentsSection` component, and tags environment panes in the sidebar.

## Consequences

- Agents and people in a project's terminal can start the project's dev server or check staging with one command, on a port that never collides with another project's, and see the same state in the browser.
- Environments are only as isolated as the user's terminals: they run as the user, with the user's network and files (the bridge's environment for `status` and `logs`, the terminal server's for panes). Nothing here sandboxes them.
- Because the pane is an interactive shell running the command as a job, the pane stays open as a shell after the command exits. A new Start closes earlier ended panes of that environment that sit at their prompt; a pane where someone is typing is left alone.
- A workspace server restart ends its panes and so its process environments; they show **stopped** (or **failed**) and are not restarted.
- Opening a repository with a `.kelp/environments` folder, or listing its environments, never runs anything from it: only a request naming one environment (Start, Stop, Check status, or `kelpmux env up|down|status NAME`) does. A `status` script is read on this thread under its 10-second deadline, and a process it detached that keeps its output open is not waited for.

## Future work

- **Containers and runtime backends**: running an environment in a container, a pod or a remote host instead of a pane, with the manifest naming the backend.
- **Routing**: a reverse proxy serving each instance at `<slug>.<domain>` with authentication, so a dev server need not be reached by port.
- Reclaiming ports, health history, dependencies between environments, and per-project or global environments outside repositories.
