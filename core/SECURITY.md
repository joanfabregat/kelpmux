# Security policy

## Reporting a vulnerability

Use [GitHub private vulnerability reporting](https://github.com/joanfabregat/kelpserver/security/advisories/new). Do not disclose suspected vulnerabilities, exploit details or credentials in public issues, discussions or pull requests. If private reporting is unavailable, contact the repository owner through an existing private channel to arrange a report; do not publish the details as a fallback.

Include affected versions or commits, prerequisites, impact and a minimal reproduction. Redact credentials and user data. Never attack a deployed instance, exhaust resources or access another user's workspace to demonstrate a problem without specific authorization.

## Supported code

Security reports about the default branch are welcome. This repository has no published release of its own yet; KelpServer builds shipped in existing KelpMux releases remain covered through [KelpMux's security policy](https://github.com/joanfabregat/kelpmux/security/policy). Older releases do not have a promised long-term support window. Reports that concern a client (the KelpMux TUI, web client or KelpClient) belong to that client's repository; KelpHub maintains its web and management code separately. When unsure, report here.

## Boundaries

KelpServer runs every terminal with the authority of the Linux user who owns it. Its local socket and state are private to that user, and peer credentials are checked, but this is not isolation against hostile processes running as the same user. A terminal client can exercise that user's authority; SSH authentication does not make executing untrusted terminal commands safe.

KelpServer contains no browser relay or static asset server; the browser relay belongs to KelpMux (`kelpmux web-relay`) and is covered by its security policy. A browser reaches a workspace only through an SSH-authenticated bridge command (`kelpserver bridge` or a client's own bridge), with the authority of that Linux user.

## File operations

The `files` stream capability (list, stat, read, write, create a folder, rename, move to the trash, delete) acts on the host where the shells run, with the server user's credentials. It grants nothing a stream connection does not already have, since any connection may type into a shell as that user; the security boundary remains the authenticated stream connection (the private, peer-checked socket, or SSH for a bridge). It never elevates privileges. In scope for reports: a file operation that acts through a symlink at the final component of a change (writes, renames, trash, delete), follows a symlink while deleting a tree, writes non-atomically, escapes its documented bounds (sizes, entry counts, paths per request, concurrent operations), blocks the server's event loop, or reaches anything the server otherwise refuses. Intermediate path components follow symlinks like a shell does, by design, as long as they stay inside the file root (below); only the final component of a change is protected. File operations refuse to remove `/`, the user's home directory or the file root itself, never cross into another file system while deleting a tree, and never open a path that is not a regular file for reading or writing. They cannot be cancelled: an operation stuck on an unresponsive file system (a hung network mount) keeps its slot, and enough of them make further file requests answer `busy` until they return or the server restarts; this is a known limitation, not a vulnerability. Out of scope: that a connection can read or delete the server user's files at all, and races with other processes of the same user, which the same-user boundary above already excludes. Front ends that relay several users' requests to one server must apply their own policy; see [the files contract](crates/server/docs/native-client-protocol.md#files-files).

### File root

Every file operation, download and client-chosen upload destination is confined to the file root: the server user's home directory, or the folder set with `--files-root` (advertised as Welcome `file_limits.root`). Paths are checked lexically against the root, then opened beneath it with `openat2(RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS)`, or by a component-by-component `O_NOFOLLOW` walk that resolves symlinks in the server where `openat2` refuses (absolute symlinks) or is missing; anything outside fails with `outside_root`. Symlinks pointing outside are listed and stat'ed as links but never followed. What the gate does: it keeps the file browser, editor, downloads and upload destinations from showing or changing anything outside the root, through any path spelling or symlink. What it does not do: it is not a sandbox. The same connection can type `cat /etc/passwd` or `rm` into a shell running as the same user, so the gate is no boundary between that user and the rest of the host; the trash and upload directories are server configuration and may lie outside the root; and a directory that another process of the same user moves out of the root while a path is being resolved can still be traversed (this is also true of `RESOLVE_BENEATH`, which guards only `..`). In scope for reports: a file operation, download or upload destination that reads, lists, writes, creates, renames, moves, trashes, deletes or downloads anything outside the root, follows a symlink out of it, or removes or changes the root itself, without such a concurrent move by the same user.

Extra roots set with `--files-extra-root` (advertised in Welcome `file_limits.roots`) widen the gate to further folders outside the primary root, each with the same guarantees on its own: a path is resolved beneath the one root it lies in, so a symlink never leads from one root into another, and a rename or trash that would move an entry into another root is refused (`cross_root`). Extra roots that overlap the primary root or each other are skipped at startup. Each root is pinned to the directory (device and inode) it was at startup: a root, or a folder above it, replaced later by someone who can change its parent (a shared data drive, say) makes requests in that root fail instead of following the replacement. In scope for reports, in addition: a file operation that reaches one root through a symlink in another, moves an entry between roots, or acts on a replaced root.

The gate's own configuration is not protected from the file browser. `workspace.json` (under `~/.local/state`, inside the default primary root) holds `files_root` and `files_extra_roots`, so a `file_write` there widens the roots when the server next starts; KelpMux's `~/.config/kelpmux/config.toml` will be in the same position. This is consistent with the same-user boundary above (a shell on the same connection can edit these files too), not a vulnerability; a deployment that needs a fixed boundary keeps the configuration file outside every root (`--state-dir` or `--config`). Command-line roots win over the file's for `kelpserver server`, but they do not help on their own: `start` records them in the file, and with no `--files-extra-root` the file's list still applies.

### Downloads

The `file-downloads` capability streams a regular file, or files and folders as one `.tar.gz` archive, from the server host to the requesting connection. It exposes nothing a stream connection cannot already read through a shell or `file_read`: the same same-user boundary applies, and anything the server's user can read can be downloaded. In scope for reports: a download that opens a device, FIFO or socket, follows a symlink while archiving a folder (symlinks are stored as links), crosses into another file system while walking a tree, exceeds its documented bounds (window of unacknowledged chunks, download bytes queued ahead of screen updates, entries, input bytes, names scanned and held by a walk, depth, concurrent downloads and threads per connection, including after cancelling), keeps running after it is cancelled, its connection leaves, or its client stops acknowledging for longer than the 10-minute stall timeout, delivers one connection's download to another connection, blocks the server's event loop or starves other connections' screen updates, or produces an archive whose entries escape their root folder when extracted (a name with `..` components or an absolute path, in the pax records or in the ustar fields a reader that ignores pax uses; names are the selected entries' own names and their descendants'). Archives carry permission bits and modification times, but no owner or group names (owner and group are 0). Out of scope: that a connection can download the server user's files at all, and races with other processes of the same user (a file changing while it is read is recorded, not prevented).
